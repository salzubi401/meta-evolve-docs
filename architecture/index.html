    Meta-Evolve Architecture

    Status

    This document defines the intended architecture of Meta-Evolve. Milestone 5 is complete, including external source evaluation through the bounded development subprocess adapter. Milestone 6 is also complete: independent native Claude and Codex proposers compose at the structural seam and remain local-only. Governance, portable runtime reconstruction, hardened execution, and later interfaces remain design targets rather than shipped behavior.

    Meta-Evolve is a programmable substrate for evaluated improvement loops. It is intended to support populations of independently contributed agents that improve artifacts, accumulate reusable experience, and eventually coordinate across machines and institutions.

    It does not claim that scaling agent count guarantees discovery, that evaluator-guided improvement is unrestricted recursive self-improvement, or that software and simulation results alone constitute validated science.

    The idea

    Most agent frameworks define a fixed harness and ask it to solve tasks. Meta-Evolve makes the harness, its components, and the improvement process programmable objects.

    Task
  defines success, constraints, evidence, and budgets

Artifact
  is the immutable object being improved

Proposer
  produces a candidate transformation or experiment

Trial
  is the immutable unit of experimental intervention

Evaluation
  measures the result and attaches evidence

SearchProgram
  decides what receives the next unit of compute

ExperienceGraph
  preserves the causal state produced by the search

    Artifacts are the durable products of improvement. Trials are the durable units of experimentation. Experience is the causal record connecting decisions, trials, and products.

    The same loop can evolve:

    • prompts and LM programs;
    • skills, tools, and memory policies;
    • complete agent harnesses;
    • multi-agent roles and communication topologies;
    • source files, packages, repositories, and multi-repository systems;
    • datasets, curricula, checkpoints, and model routers;
    • hypotheses, experiments, claims, and scientific artifacts;
    • evaluators, schedulers, and search policies themselves.

    Principles

    Artifacts are the unit of progress

    Thousands of agents should not edit one branch or share one conversation. Agents perform bounded work over an immutable graph of artifacts. They communicate through proposals, artifacts, evaluations, evidence, skills, claims, and explicit causal links.

    Execution is private; experience is shared

    Each worker receives an isolated workspace and explicit capabilities. It may terminate after one assignment. Durable collaboration happens through committed artifacts and governed experience, not a long-lived agent process or a globally writable directory.

    Durable logical state is projected from immutable records

    Immutable domain records and their append-only transition events are the source of durable logical truth. Populations, frontiers, leaderboards, search statistics, knowledge indexes, and training datasets are rebuildable projections. Ephemeral worker liveness, caches, credentials, service health, and queue estimates are disposable infrastructure state; when they affect experiment semantics, the observed condition is recorded.

    Evaluation is a protocol object

    An evaluation includes the evaluator, environment, measurements, uncertainty, constraints, evidence, resource use, and visibility—not just a scalar score. Infrastructure failures and policy violations remain distinct from poor task performance.

    Search and context policies are explicit

    Parent selection, proposer assignment, context retrieval, agent-directed experience access, mutation, admission, migration, replication, promotion, and stopping must be inspectable policies or audited capabilities rather than hidden orchestration code.

    Proposal and promotion are separate

    A system may propose successors to its own code or policy. It may not grant itself authority, change hidden evaluation, raise its budget, erase failures, or promote itself. Those controls remain outside the candidate's mutation boundary.

    Relative to an enclosing trial, every configurable field belongs to one authority zone:

    Candidate-controlled
  candidate implementation, prompts, tools, context strategy, search heuristics

Experiment-controlled
  task distribution, seeds, evaluator environment, budgets, data splits

Governance-controlled
  permissions, promotion rules, evaluator admission, identity, visibility, licensing

    An effective MutationSurface records what a trial may modify, which interfaces remain fixed, which validation is required, and the trial's authority ceiling. A candidate may propose changes outside that surface, but the coordinator rejects rather than applies them.

    Local and distributed runs share semantics

    A laptop implementation and a future network consume the same work, artifact, evaluation, and event contracts. Scaling changes backends and trust policies, not the meaning of an experiment.

    Architectural layers

    Task layer
  artifact contract, objectives, constraints, evaluator, authority boundary

Search layer
  context, selection, mutation, archives, allocation, migration, stopping

Execution layer
  agent SDKs, workspaces, sandboxes, evaluators, workers

Data layer
  events, artifacts, experience graph, knowledge, training views

    These are logical boundaries. The deterministic kernel can run entirely in memory; the durable local implementation can run them in one Python process with SQLite and a local artifact directory.

    The delivery plan separates three scopes:

    Kernel
  Task, Artifact, Proposal, Trial, TrialOutcome, Evaluation, Evidence,
  SearchDecision, immutable records, and deterministic transitions

Standard library
  proposers and runtimes, evaluators, artifact codecs, search policies,
  context policies, workspaces, stores, and experience queries

Optional systems
  federation, signatures, reputation, training views, remote scheduling,
  licensing propagation, and domain-specific scientific institutions

    Optional systems must not add ceremony to the local kernel unless a demonstrated use case requires a new general semantic contract.

    Core primitives

    Task

    A task is a versioned experimental contract:

    Task(
    artifact_kind="git-tree",
    objectives=[
        Objective("correctness", satisfy=1.0),
        Objective("latency", direction="minimize"),
    ],
    evaluator=EvaluatorRef("kernel-evaluator@3"),
    budget=Budget(evaluations=1_000),
)

    Tasks define accepted artifacts, ordered objectives, evaluator versions, budgets, and reproducibility requirements. Evaluation, budgets, governance, and promotion remain outside candidate authority.

    R1 does not add provider authority fields to Task. A proposer preflight receives only artifact kind and representation, ordered objectives, the exact effective run budget, and normalized experience declaration. Provider-specific workspace, tool, approval, network, output, and interruption configuration stays at the adapter edge until a concrete adapter demonstrates a smaller portable declaration is required.

    Task identity remains the established canonical encoding. R1 makes no Task schema or identity-projection change, preserving canonical bytes, TaskId, RunId, and named random substreams.

    Artifact

    An artifact is immutable, typed, content-addressed, and linked to its parents. Its semantic kind is separate from its storage representation:

    Artifact
├── identifier and content digest
├── semantic kind and schema version
├── storage representation
├── parent references
├── payload reference
├── declared interfaces
├── provenance and contributors
└── governance and licensing metadata

    For example, a harness, policy, or skill set may all use a git-tree representation while exposing different schemas and interfaces. GitTreeArtifact, TextArtifact, HarnessArtifact, and similar names are ergonomic typed constructors or views over the common envelope, not necessarily a class hierarchy. Record objects such as proposals, trials, and evaluations are not artifacts merely because they are versioned.

    Payload translation is owned by the codec registered for the exact semantic (kind, representation) pair. The registry resolves that pair and exposes its declared interfaces; it does not normalize durable identity fields or grant the codec authority over artifact ids, lineage, evaluation, budgets, or promotion. The coordinator depends only on the codec index: seeds, proposed candidates, evaluator inputs, and read-only result views cross that one boundary without an artifact-domain branch.

    Registry-aware result reopening is decoding authority only. The supplied registry contributes the codecs that may interpret stored payloads, while the committed run projection chooses which artifact kind is actually read. A read-only Run gains no ability to mutate history, execute or resume work, evaluate candidates, spend budgets, or promote artifacts.

    Proposer and agent

    A proposer is the kernel role that produces a candidate transformation or experiment. An agent is one proposer implementation. Other implementations include a plain callable, deterministic mutator, LM program, trained policy, human workflow, or composite system.

    The core protocol does not depend on one model vendor or on terminal scraping. R1 accepts a non-callable structural object implementing only propose(parent, context) and keeps full runners at the same boundary. The context carries candidate-visible randomness, logical step, ordered objectives, the exact pushed bundle, and optional scoped experience; it carries no Task, evaluator, or promotion authority.

    A configured native proposer declares one local ComponentRef retaining that exact object. Its adapter-owned, secret-safe identity payload hashes every safe behavior-affecting field into the component version. Core records and compares that declaration without reflecting over arbitrary provider state. Bound methods are execution details, not identity objects. These local declarations are intentionally non-resumable.

    Proposal

    A proposal describes an intended transformation or experiment before execution:

    Proposal(
    parent_ids=(artifact_id,),
    operator=OperatorSpec(kind="patch"),
    hypothesis="The cache layout causes the remaining regressions.",
    predicted_outcomes={"latency": "5-10% lower"},
    derived_from=(
        ExperienceRef(
            run_id=run_id,
            kind="evaluation",
            occurrence_id=evaluation_id.value,
        ),
        ExperienceRef(
            run_id=run_id,
            kind="evidence",
            occurrence_id=evidence_id.value,
        ),
    ),
)

    Predictions enable calibration and make failed work useful. Proposal types may include patches, prompt edits, skill mutations, merges, experiments, replications, training jobs, evaluator changes, and policy changes.

    Any prediction used for calibration must be causally committed before the evaluator reveals the predicted evidence. Some workflows commit a proposal before applying it; others produce a proposal and candidate together but must commit both before evaluation begins.

    Trial and outcome

    A trial is the immutable experimental unit joining a search decision, task, parents, proposer, operator, context, budget, environment, and seed. TrialSpec is the requested intent; an accepted Trial gives it stable identity.

    SearchDecision → TrialSpec → Trial
                           ├── delivered by WorkItem
                           ├── retried by WorkAttempt or lease
                           ├── produces TrialOutcome
                           │   ├── Proposal
                           │   ├── Artifact occurrence(s)
                           │   ├── trace and observations
                           │   └── usage or typed failure
                           └── receives Evaluation(s)

    A retry of delivery does not create a new trial. One proposal may be tested by several trials, one trial may produce several artifacts, and an outcome may receive multiple evaluations. ExperienceNode remains a projection over these canonical write records.

    Evaluation and evidence

    Evaluation(
    artifact_id=artifact_id,
    evaluator=evaluator_ref,
    environment=environment_ref,
    objectives={"correctness": 1.0, "latency_ms": 4.2},
    uncertainty={"latency_ms": 0.1},
    evidence_ids=[test_report_ref, benchmark_log_ref],
    resources=Usage(tokens=42_000, wall_seconds=93),
)

    Evidence may be a test report, proof object, measurement log, replication, simulator output, review, or physical observation. Claims point to supporting and contradicting evidence and retain their scope and validation state.

    Population

    A population is a policy-defined view over artifacts. It may be one incumbent, a Pareto frontier, a quality-diversity archive, an island, a novelty niche, or a set awaiting replication.

    Membership is derived from admission, archive, migration, rejection, and promotion events rather than represented by moving mutable files between folders.

    Policy and SearchProgram

    A SearchProgram has one durable decision method and composes the policies controlling improvement:

    class SearchProgram(Protocol):
    archive: ArchivePolicy

    def next(self, state: SearchState) -> SearchDecision: ...

    The implemented decision vocabulary is TrialSpec | ArchiveUpdate | Stop. ArchiveUpdate records an evaluated candidate's admission or rejection and the resulting rank-ordered membership without performing work or consuming budget. Later decisions such as TrialBatch, ReplicationSpec, and MigrationSpec can extend the same method surface. A trial identifies parents, proposer, typed operator specification, context policy, budget, and deterministic seed; the coordinator executes the fixed propose, capture, evaluate, and record protocol.

    Most algorithms are compositions of small Selector, Allocator, OperatorPolicy, ContextPolicy, ArchivePolicy, and StopPolicy objects. A custom algorithm may implement next directly. The method is re-entered from committed projected state at every logical step, so a policy's Python call stack is never the durable state of a run.

    The implementation should provide simple baselines before sophisticated policies: independent best-of-N, greedy improvement, population evolution, Pareto selection, islands, novelty search, MCTS-style expansion, and bandit allocation.

    A serialized PolicyArtifact can itself become an optimization target. That is the bridge from artifact improvement to improvement of the search process.

    The programming model shows the common loop and sketches how these algorithms, experience-aware agents, harness evolution, and policy meta-evolution compose through the same API.

    WorkItem

    A work item is the boundary between logical scheduling and execution:

    WorkItem(
    trial_id=trial_id,
    task_id=task_id,
    action="propose",
    artifact_id=parent_id,
    proposer=proposer_ref,
    context=context_bundle_ref,
    experience=ExperienceGrant(
        run_id=run_id,
        task_id=task_id,
        trial_id=trial_id,
        as_of=logical_step - 1,
        spec=experience_spec,
    ),
    budget=Budget(tokens=100_000, wall_seconds=1_800),
    idempotency_key="...",
)

    Workers lease work for bounded periods. Completion, expiration, retry, cancellation, and duplicate execution are explicit transitions. The work item and its attempts are delivery identities, distinct from the logical trial identity.

    Event

    Events are immutable facts such as:

    TaskPublished        ProposerRegistered    PolicyDecisionMade
PolicyDecisionExplained
ContextPolicyDeclared
TrialStarted         WorkRequested         WorkLeased
ProposalSubmitted    ArtifactCreated       TrialCompleted
EvaluationRequested  EvaluationCompleted   ArtifactAdmitted
ArtifactRejected     ArtifactMigrated      ReplicationRequested
ContextSelected      ExperienceQueried     ExperienceOpened
KnowledgeDistilled   TrainingViewMaterialized

    Every event carries schema version, logical ordering, actor, scope, correlation and causation identifiers, relevant trial and artifact references, policy/environment versions, and public or private payload references.

    Immutable domain objects may be stored as normalized append-only records or content-addressed envelopes. Events are authoritative for the fact that transitions occurred; object records are authoritative for object content. A durable adapter writes an object and its corresponding transition event atomically. Projections remain disposable and rebuildable.

    Experience graph

    Long-horizon search produces a causal graph of trials rather than a collection of final answers.

    Task
└── Run
    └── ExperienceNode
        ├── parents and causal inputs
        ├── proposal and agent/harness version
        ├── context snapshot and prompts
        ├── tool and execution observations
        ├── produced artifacts
        ├── evaluation, reward, and evidence
        ├── policy decision and search metadata
        ├── resource consumption
        └── provenance and access policy

    ExperienceNode is a read model, not a replacement for typed writes. Proposals, artifacts, evaluations, work items, and events remain explicit; the graph connects them for search and learning.

    The derivation subgraph is acyclic: a trial can only derive from experience that already exists at its logical step. Other typed relationships such as similar_to, contradicts, reviews, or replicates are cross-links and need not form a DAG. Content identity is also separate from occurrence identity: two trials may independently produce identical bytes while retaining distinct hypotheses, parents, contributors, and causal histories.

    class ExperienceGraph(Protocol):
    def node(self, ref, query): ...
    def ancestors(self, ref, query): ...
    def children(self, ref, query): ...
    def siblings(self, ref, query): ...
    def frontier(self, query): ...
    def trace(self, ref, query): ...
    def state_at(self, query): ...

    M3.1 implements this protocol as an immutable in-memory projection over the validated committed run stream. ExperienceQuery(task_id, run_id, as_of) carries scope and an optional inclusive logical-step boundary, but no reader identity. ExperienceRef(run_id, kind, occurrence_id) names an existing occurrence identity, never a content digest or event position. One node aggregates one trial occurrence; exact decision, explanation, proposal, artifact-creation, outcome, evidence, and evaluation records retain their committed values and event ordering.

    Ancestors exclude the target. Siblings include it. Frontier means visible causal leaves, not archive membership. Parent relations are derived from declared parent artifact occurrences to the trials that produced them, preserving declared order and deduplicating repeated relations. Node collections are ordered by (logical_step, trial_id). A trace covers the target trial and its accessible ancestors — their attached records ordered by event sequence and a fixed intra-event record-kind order.

    The M3.1 local projection uses one content-free access denial for missing, wrong-kind, wrong-task, wrong-run, future, hidden, retracted, and non-local direct targets. Collections omit inaccessible nodes and never traverse through them. Locality, visibility, and retraction remain a private projection test seam; they do not introduce reader grants, durable trust metadata, or retraction events.

    The logical interface can later compose structured filtering, semantic similarity, dataset scans, and durable backends. The first durable backend should remain ordinary SQLite plus content-addressed files. Specialized graph, vector, warehouse, or object-store backends can be introduced behind the interface when measurements justify them.

    The graph is a read model, not a mandatory graph database. Historical state can initially be reconstructed by replaying events. Materialized snapshots are optional caches for faster reconstruction and never replace the event stream as the source of truth.

    Memory types

    Type Contents Purpose
    Declarative facts, claims, specifications what is believed
    Procedural skills, tools, policies, executable methods how to act
    Episodic messages, tool calls, observations, local traces what happened in one execution
    Experience causal alternatives, artifacts, rewards, failures, decisions what to explore, reuse, compare, or learn from

    Distilled knowledge retains links to the experience and evidence from which it was derived.

    Temporal state

    Causal facts are immutable, but frontier priority, visits, cumulative reward, island membership, value estimates, and leases can change. Every policy decision must be reproducible from the state it observed at its logical step.

    This prevents future-information leakage when experience is converted into training data. It also makes concurrent runs auditable even when workers finish out of wall-clock order.

    For the M3.1 projection, state_at(ExperienceQuery(..., as_of=n)) includes facts at logical step n and every earlier step. Bootstrap is step zero. A later node or record receives the same opaque denial or omission as any other inaccessible occurrence.

    ContextPolicy

    Automatic experience retrieval is a policy rather than a default global memory:

    class ContextPolicy(Protocol):
    def select(self, task, candidate, graph, spec) -> ContextBundle: ...

    Implementations can select ancestors, strong siblings, related failures, similar tasks, diverse strategies, or no prior memory. The retrieved items, selection reason, and context cost are recorded.

    M3.2 declares one non-default run-level ContextSpec(policy, max_records, max_chars) after bootstrap evaluation. A transparent search-program wrapper stamps that policy reference into successor trials without changing decisions, descriptions, or named random streams. The generic coordinator selection operation commits after the decision explanation and before proposer execution; bootstrap has neither user context nor a policy reference.

    The selected ContextBundle is immutable and stores exact typed source records, reference order, canonical rendering, reason, truncation, and separate ContextUsage. Record and rendering bounds are independent. Context facts are projected for inspection but excluded from future selection candidates, which prevents recursive bundle growth. Reproduction consumes the committed bundle without rerunning selection or rendering.

    Reuse can reduce repeated failures and accelerate convergence, but excessive reuse can anchor search and reduce diversity. Exploration versus reuse is therefore an explicit, measurable, and evolvable decision.

    Agent-directed experience access

    Policy-selected context is only one access mode. Authorized agents may also explore prior work during execution, deciding what to search, open, compare, and reuse instead of receiving only a compressed summary chosen in advance. This generalizes the full-history filesystem used by Meta-Harness while preserving typed lineage, temporal reconstruction, and access control.

    class ExperienceReader(Protocol):
    def search(
        self, *, record_kinds=(), failure_kinds=(), as_of=None, limit=None
    ): ...
    def open(self, ref, *, as_of=None): ...
    def ancestors(self, trial_ref, *, as_of=None, limit=None): ...
    def siblings(self, trial_ref, *, as_of=None, limit=None): ...
    def compare(self, left_trial_ref, right_trial_ref, *, as_of=None): ...

    ExperienceReader is an agent-facing, read-only, scoped capability over the internal ExperienceGraph. M3.3 declares one run-level ExperienceSpec after bootstrap evaluation and after any context declaration. Every successor receives a fresh ExperienceGrant bounded to the same task and run and to as_of=trial.logical_step - 1; bootstrap receives no reader. An as_of argument may narrow that boundary but never widen it. Queries have independent operation, result, structured-record, and rendered-character budgets. Persisted execution observations may be exposed; private data, secrets, hidden evaluator state, and unrecorded model reasoning are not implied to be available.

    During a proposal call, the reader holds only its grant, a view of its own committed operations, a grant-scoped experience graph, and a narrow append capability bound to its trial, correlation, and pull-audit fact types; it never receives the coordinator or the event store. Each call commits ExperienceOperationAttempted before validation, followed by exactly one success with the returned value, opaque denial, or content-free exhaustion. This is deliberate mid-proposal append authority, not coordinator access. Denied and exhausted attempts consume no result, record, or character capacity; later swallowed post-exhaustion calls remain charged and audited. Replay validates the ledger and returns committed outcomes directly.

    Every exact result set, opened record, comparison, rendering, truncation decision, and returned reference is therefore recorded. M3.4 lets a proposer declare which of those observations it used. The declaration must be a unique ordered subsequence of its committed push-then-pull observation ledger; merely observing a record does not create a derivation edge.

    The local experience milestone enforces logical time, read budgets, and observation recording because they are required for causal validity. Principal identity, licensing, and multi-tenant visibility policies may remain single-user stubs until the trust and federation milestones.

    Two complementary modes therefore share the same underlying records:

    push: ContextPolicy selects a bounded ContextBundle before execution
pull: ExperienceReader lets the agent explore authorized history during execution

    The pull interface may be exposed as structured tools or as a read-only filesystem projection for coding agents:

    experience/
├── trials/<trial-id>/
│   ├── artifact/
│   ├── proposal.json
│   ├── evaluation.json
│   └── trace.jsonl
├── indexes/
└── run.json

    The filesystem is a compatibility and usability view, not the durable data model. Opening a projected file must have the same authorization, logical-time, provenance, and audit semantics as calling the structured reader.

    Programming harnesses

    The desired programming style resembles DSPy or PyTorch, but the target is an executable harness rather than only an LM pipeline:

    class ResearchHarness(meta.System):
    planner = meta.LM("problem, evidence -> hypothesis, predictions")
    executor = configured_native_proposer
    memory = meta.ExperienceMemory(policy=meta.DiverseRetrieval())
    tools = meta.Toolset(["python", "literature", "simulator"])
    workflow = meta.Workflow(...)

    def run(self, problem): ...

    Mutation surfaces are typed and explicit:

    planner_prompt = meta.TextParam(...)
planner_program = meta.ProgramParam(...)
memory_policy = meta.PolicyParam(...)
tools = meta.ToolsetParam(...)
agent_code = meta.CodeParam(...)
topology = meta.TopologyParam(...)
model_router = meta.ModelParam(...)

    A harness manifest identifies mutable components and external controls. Candidates may change planning, prompts, skills, memory, tools, workflow, or routing. They may not change hidden evaluation, secrets, permissions, resource limits, audit history, or promotion policy.

    Nested improvement loops

    Execution
  a harness performs a task and produces a trace

Learning / evolution
  an optimizer uses traces and evaluations to propose a better harness

Meta-learning / meta-evolution
  an outer optimizer compares and improves the optimizer or SearchProgram

    Formally:

    trace_t       = Run(harness_theta, task_t)
theta_(t+1)   = Update_phi(theta_t, trace_t, evaluation_t)
phi_(k+1)     = MetaUpdate(phi_k, heldout_performance(Update_phi_k))

    Each loop has a separate budget, evaluator, data boundary, and promotion rule. Meta-improvement evaluates fresh runs on held-out task distributions rather than accepting optimizer self-reports.

    Inner and outer runs use the same kernel. An outer evaluator launches a versioned suite of bounded inner RunSpecs, aggregates their evidence, and returns an evaluation of the outer HarnessArtifact or PolicyArtifact. The candidate cannot modify the episode suite or any enclosing budget or promotion rule. See inner and outer loops for the API sketch.

    Training views

    Training data is a governed projection of experience:

    successful causal paths          → SFT trajectories
sibling attempts and rewards     → preference pairs
same-state candidate groups      → group-relative learning cohorts
frontier decisions and outcomes  → value/allocation-policy examples
failure and repair clusters      → skill-distillation datasets

    Each materialized example retains exact source nodes, observed context, evaluator and environment versions, logical decision time, reward semantics, and access-policy lineage. Retraction or invalidation of a source must be traceable to dependent datasets, skills, and checkpoints.

    Model training does not need to live in the kernel. External trainers consume DatasetArtifacts and return versioned CheckpointArtifacts.

    Workspaces, proposer adapters, and sandboxes

    The execution layer exposes the structural proposer and proposer-runner boundaries specified by the programming model, plus the independent WorkspaceProvider and SandboxProvider ports already proven in M5. A native adapter owns its async loop, provider sessions and turns, streaming, prompt rendering, tools, approvals, workspace lifecycle, structured-output mechanism, interruption, cleanup, and evidence conversion. Core owns artifact occurrence identity, parents, proposal normalization, evaluation, budgets, context and experience scope, and commitment.

    R1 intentionally introduces no shared provider execution transport, provider-options mapping, or canonical tool vocabulary. One optional validate_run hook rejects unsupported artifact, objective, budget, or experience declarations before provider or workspace activity. A proposer-raised CapabilityError retains its type and message; unexpected validator exceptions are sanitized without losing their cause.

    R2 binds meta_evolve.claude.Claude directly to that seam. The adapter owns a worker-thread event loop, one fresh ClaudeSDKClient, a private WorkspaceProvider, deterministic prompt rendering, and a closed native profile. Ordinary typed init reports exactly Read, Edit, and Write and no MCP servers; native schema output conditionally adds StructuredOutput. Pull-enabled R4 runs add one verified in-process MCP server and select the pull turn ceiling rather than the ordinary one; the two default to four and 12 and are both declarable. setting_sources=[], strict_mcp_config=True, the claude_code preset, acceptEdits, and an enabled sandbox with an empty network allowlist are configured mechanisms, not hostile-code containment. Provider prose is discarded; workspace capture is the sole candidate authority, and evaluator execution begins only after the provider workspace is disposed.

    R3 binds meta_evolve.codex.Codex independently to the same seam. It owns one fresh worker, disposable private CODEX_HOME, client, ephemeral thread, and medium-effort turn. The private home copies only a regular file-backed OAuth record at mode 0600 and writes an exact-cwd untrusted project entry. Typed readback must confirm the requested model, deny-all policy/reviewer, workspace-write sandbox, exact cwd, ephemeral lifecycle, and instruction sources before mutation records are accepted. Ambient home configuration is excluded; project .codex authority remains inactive; exact workspace AGENTS.md content remains candidate input through native discovery.

    R4 pull runs retain thread-level deny_all and add an authenticated adapter-owned loopback HTTP MCP server through literal private-home TOML. Granular configuration approves exactly the six experience tools and leaves all other native and MCP authority under deny_all. Typed full MCP status must confirm bearer authentication, server identity, the exact tool inventory, and annotations before the model turn starts. The five reader operations are read-only; derivation declaration is non-destructive and state-changing.

    Two boundaries of that verification are exact. Readback proves only what the typed thread-start response reports, so it detects escalation of the model, policy, sandbox, cwd, lifecycle, effort, and instruction sources; project configuration that changes nothing reported there, such as registering an MCP server, is prevented by the untrusted project entry rather than detected by readback. Separately, the pinned SDK builds the native process environment by overlaying its own variables on the parent environment, so the private home isolates configuration files but the native session inherits the host environment. Unlike Claude, which pins an empty environment, Codex offers no supported way to clear it. Do not run the Codex proposer in a process holding environment secrets it should not see. Under workspace-write the native sandbox also leaves /tmp and $TMPDIR writable; those writes never reach the candidate, because only the captured workspace is candidate authority.

    The Codex adapter exposes no native configuration dictionaries, effort, timeout, authentication path, steering, fork, retry, or resume controls. Native shell, discovery, and possible provider-owned tools remain irreducible; there is no exact tool ceiling. Workspace-write is a configured mechanism only and does not claim network or hostile-process containment. Workspace capture is the sole candidate, provider prose is discarded, and schema-constrained final text is independently revalidated as evidence only.

    The M6.0 measurements remain binding adapter requirements. Codex token total is input plus output because cached input and reasoning output are inclusive subsets. Claude token total adds ordinary input, cache creation, cache read, and output, while its cache buckets remain inclusive detail. Unreported dimensions stay unknown: Codex exposes neither cache-write tokens nor cost, and Claude cost is provider evidence rather than a core budget or cross-provider equivalence. Both adapters independently revalidate structured output.

    Provider claims require machine evidence. Typed tool records, native status, configuration readback, workspace snapshots, and canaries may support a claim; final model text may not. The pinned Claude interruption sample stopped its delayed write. The pinned Codex sample reached a terminal interrupted event but left the command alive. A Codex adapter therefore cannot accept a deadline that requires reliable in-flight cleanup until a new mechanism is separately verified. Configuration verification and sampled behavior do not claim hostile code containment.

    This produces an intentional wall-budget asymmetry. Claude accepts an unbounded wall budget or a finite budget no tighter than its configured per-proposal timeout, interrupts on that timeout, drains to terminal accounting, disconnects, and disposes. Codex rejects every finite wall budget until its cleanup evidence changes; it does not emulate Claude mechanics and has no adapter timeout. An unresponsive Codex turn can therefore block meta.run indefinitely. For Claude, a reportable timeout requires exact drained usage. For either adapter, cleanup failure overrides an apparent success or typed failure while retaining any accounting already known.

    The wait after interruption is itself bounded: a configured deadline that could block forever on an unresponsive session would not be a deadline. When the bounded grace expires the adapter abandons the stream, which loses exact terminal accounting and therefore aborts the local run instead of inventing usage. A proven deadline also outranks the transport fault it causes: because interruption is how the deadline is enforced, the resulting fault is recorded in the timeout's details rather than reported as an unexplained infrastructure failure.

    The shipped workspace and sandbox boundaries are synchronous because the local kernel is synchronous; a later asynchronous runtime adapts at its own edge rather than infecting these contracts. Workspace providers materialize immutable artifacts into private writable views and capture candidate content, while the coordinator remains authoritative for artifact occurrence identity, parents, provenance, and commitment.

    M5.1 implements utf8-tree-v1, DirectoryWorkspaces, and an exact-file PatchProposer. This filesystem cycle deliberately proves real materialization, capture, cleanup, and failure behavior before subprocess execution becomes its first load-bearing consumer. It is a development authority boundary, not hardened isolation.

    M5.2 adds immutable process declarations/results and DevelopmentSubprocessSandbox. The port validates only declaration integrity; each provider owns its authority policy so a future container or remote provider can permit a different executable form without a coordinator branch. The development adapter admits an absolute executable, a normalized cwd that resolves inside the workspace, and an exact declared environment. It starts a new POSIX session, captures stdout and stderr independently, and terminates the whole process group on timeout or per-stream byte overflow. Overflow is an execution failure, not truncate-and-continue behavior. Completion is reported only after both output streams reach end-of-file: a leader that exits while group members still hold its pipes runs to the declared bound rather than claiming complete capture. A broken workspace root is an infrastructure failure, not a caller policy violation.

    Process and descendant cleanup has the same honesty invariant as M5.1 workspace disposal: a lifecycle-control failure overrides apparent completion, because the system cannot claim a bounded execution while owned work may remain. Elapsed monotonic time is occurrence data and does not participate in artifact content identity. The shipped adapter controls cwd, environment, wall time, and output only; it does not isolate network, CPU, memory, syscalls, or hostile code.

    M5.3 adds CommandEvaluator above those two replaceable ports. It remains a callable evaluator with a declared local ComponentRef, so Task normalization and the existing callable-evaluator runner carry it through the coordinator. The coordinator does not know about commands, workspaces, source trees, or sandbox implementations. A general Task rule accepts any callable that declares a valid local evaluator component retaining that exact callable and invokes its optional structural validate_task hook.

    The command adapter requires SourceTree, one matching objective, and direction-consistent passing and failing scores. It materializes a fresh workspace per candidate, always disposes it, preserves M5.2 process failures, and maps completed exits through the versioned 0 pass, 1 fail, other evaluator-failure protocol. Environment identity and bounded process output are immutable evidence. Exact argv remains evaluator-owned; its full semantics are committed by the digest-backed component version rather than copied into candidate-visible evidence. Disposal failure takes precedence while retaining prior classification, evidence, and measured wall usage.

    The development boundary prevents proposal-time patches from including an evaluator-owned grader because only the candidate SourceTree is materialized and captured. It does not prevent hostile runtime code from probing the host filesystem; that requires a stronger sandbox provider at the same port.

    Milestone 5 is complete at this boundary. A failing command exit is rankable task performance only when it is the declared exit 1; evaluator, timeout, resource, policy, and infrastructure failures remain typed non-rankable outcomes. Artifact content and the canonical example's semantic lineage are deterministic, while monotonic wall time is an observed occurrence value. Durable storage supports reopened best-artifact and lineage queries, but local patch and command components are not reconstructible, so cold resume fails with CapabilityError without changing history or workspaces. Milestone 6 shipped native SDK proposers as local-only components; portable reconstruction of patch, command, and native SDK proposer components remains later work.

    SDK proposer adapters own provider-specific model sessions and tool callbacks. Stronger sandbox providers may enforce filesystem, network, secret, and additional resource policies at the same port.

    Structured experience remains a core authority even when exposed through provider-native MCP or custom-tool mechanisms. ExperienceGrant, ExperienceReader, logical time, charging, auditing, observations, and derivation validation retain their existing meaning. Completed reads and audit facts survive typed runtime failures. No generic MCP layer or filesystem-shaped experience contract is introduced in M6.

    After an interrupted or lost provider execution, execution and accounting are unknown unless non-execution is proven. An adapter must not translate an unknown usage dimension to zero. The adapters' internal ExecutionAccountingUnknown extends the proposer escape boundary used by audited-reader infrastructure: it aborts the local structural run instead of committing a fabricated logical failure, and carries no retry or resume claim. Both capture postconditions after a completed provider failure but never commit partially edited files as a failed candidate. Codex cancellation requests native interruption and drains/closes where possible, but its measured descendant cleanup remains unconfirmed. Structural native proposers remain local, manifest-free, and rejected by durable-local.

    R4 binds both providers to one private trial-local experience session without adding a public type, port, coordinator branch, or durable schema. Sequential opaque handles replace adapter-authored ExperienceRef envelope fields in pushed context; record values and policy-rendered content stay exact and may themselves contain durable identifiers. Pulled references enter through the same pure ordering function as observation_ledger(), including comparison interleaving, and repeats retain their first handle.

    All valid reader calls still enter the authoritative audited reader and consume its exact budgets. Binding schema failures and unknown handles do not create operations. Expected denial and the first audited exhaustion return content-free native errors; exhaustion then latches further reads to prevent retry-driven audit growth. Declaration enters neither the reader nor its audit, so it stays available after exhaustion and a spent read budget never costs an otherwise valid candidate. A declaration is a unique ordered subsequence of observed handles, with the last valid declaration winning and invalid declarations leaving it intact.

    Unexpected reader/store faults latch and make provider mutations inadmissible. Claude requests interruption and drains before cleanup. Codex has no reliable interrupt guarantee, so it drains for the existing 60-second bound while discarding the workspace, then preserves the existing unknown-accounting and cleanup precedence. Native structural proposers remain local-only and non-replayable; registered deterministic proposers retain cursor replay.

    M6 adds no production provider abstraction and does not promote provider-specific session, tool, approval, or interruption details into core. Shared conformance does not claim model, quality, token, cost, compute, wall, tool, environment, containment, or interruption parity. Codex writable-root tightening for /tmp and $TMPDIR remains a separately measured follow-up.

    Git worktrees may be one WorkspaceProvider, not a universal coordination model. A shared network workspace means shared durable artifacts and experience, not simultaneous unsynchronized writes to one checkout.

    Scientific discovery

    A scientific loop adds typed hypotheses, experiments, claims, evidence, review, and replication:

    Problem
  → Hypothesis
  → ExperimentProposal
  → bounded execution or simulation
  → Evidence
  → claim update
  → adversarial review
  → independent replication
  → promotion, revision, or falsification

    Different agents may specialize in ideation, implementation, experiment design, analysis, criticism, replication, and distillation. Disagreement is preserved and can trigger allocation of additional compute.

    Simulation performance is not automatically a scientific discovery. Tasks define evidence ladders ranging from assertions and executed analyses through proof checks, uncertainty-aware simulation, independent computational replication, expert review, and physical replication.

    Toward an open agent network

    The initial system is local, but its contracts anticipate independent contributors:

    Contributor publishes signed agent or evaluator version
        ↓
Scheduler matches capabilities to a bounded WorkItem
        ↓
Worker executes in an isolated environment
        ↓
Artifacts and evidence are committed by content digest
        ↓
Independent evaluators verify promotion-sensitive results
        ↓
Experience, lineage, reputation, and credit projections update

    Federation should exchange signed, policy-filtered artifacts and experience subgraphs rather than begin with one globally writable database. Operators may retain private events and data while publishing permitted claims, artifacts, evaluations, skills, and provenance.

    Permissions, attribution, licensing, embargoes, and retractions follow derivation edges. A summary, embedding, skill, dataset, or checkpoint does not silently escape restrictions attached to its source experience.

    The path is incremental:

    1. Deterministic in-process kernel.
    2. Local SDK agents, evaluators, workspaces, and sandboxes.
    3. Durable single-host runs with crash recovery.
    4. Trusted remote workers and lease-based scheduling.
    5. Contributed agents, tasks, evaluators, and compute.
    6. Federated experience and verification networks.
    7. Domain-governed scientific institutions and physical replication.

    Boundaries with adjacent systems

    DSPy

    DSPy programs and optimizes modular LM pipelines. Meta-Evolve programs and evolves populations of executable systems, which may contain DSPy programs. DSPy should be a first-class integration and an inner optimizer, not the foundation of the runtime.

    EvoSkill and Meta-Harness

    EvoSkill-style skill discovery is expressed by evolving SkillSetArtifacts from clustered failures and evaluating them on held-out tasks. Meta-Harness-style improvement is expressed by evolving HarnessArtifacts with explicit mutation and authority boundaries.

    CORAL and coding-agent populations

    Parallel coding-agent optimization becomes one configuration: the evolving artifact is a repository, SDK agents propose successors in isolated workspaces, evaluators run task graders, and a population policy selects and migrates candidates and knowledge.

    Experience Graphs / Trellis

    Trellis motivates treating agent search state as a durable, governed, temporal, queryable data foundation. Meta-Evolve adopts that logical requirement while focusing on the programmable control plane, execution contracts, evolvable harnesses, contributor protocol, and federation. The prototype should use conventional storage before attempting a specialized database.

    Invariants

    1. Every candidate has an immutable artifact identity and provenance.
    2. Every logical experiment has a stable trial identity distinct from delivery attempts and retries.
    3. Every selection claim identifies its evaluator, environment, policy, and budget.
    4. Failures, timeouts, invalid executions, and poor scores remain distinguishable.
    5. Candidates cannot modify the controls that validate or promote them.
    6. Predictions used for calibration are committed before predicted evidence is revealed.
    7. Distributed retries and duplicates do not corrupt logical history.
    8. Every policy decision can be reconstructed from the state, exact context, and deterministic randomness it observed.
    9. Shared experience enters an agent through a committed context bundle or an audited, scoped experience reader with exact recorded results.
    10. Derived knowledge and datasets retain provenance, access constraints, and retraction links.
    11. Scientific claims retain scope, uncertainty, contradictions, and replication state.
    12. Prototypes and research hypotheses are never described as deployed network behavior.
