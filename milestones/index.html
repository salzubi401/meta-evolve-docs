    Meta-Evolve Milestones

    Purpose

    This roadmap grows Meta-Evolve through small, testable vertical slices. Every milestone must produce a runnable demonstration, preserve the contracts established by earlier milestones, and add only the infrastructure required by its acceptance tests.

    The first product target is a local, extensible improvement system in which a user can define an artifact, task, evaluator, proposer, search policy, and context policy; run a bounded experiment; let agents inspect prior work; replay or resume the run; and compare results under equal budgets. Harness evolution, meta-evolution, trusted concurrency, and federation build on that local product.

    The harness-evolution demonstration (milestone 8) is the flagship product demo — "point this at your agent and eval set, get a measurably better agent, and inspect exactly why each change was kept." Earlier milestones should keep that demonstration in view rather than treating it as a distant capstone.

    Before the numbered milestones, a disposable API spike validated the user-facing interface against both deterministic code and a real model. The spike is a design probe, not a shortcut into the durable implementation. It is complete; see its status below.

    Development rules

    1. Every milestone has one canonical example that runs with a documented command.
    2. Every new port has an in-memory or deterministic reference adapter and a conformance suite.
    3. The coordinator contains no branches for particular artifact types, proposers, evaluators, or search policies.
    4. Durable behavior is specified through domain events and observable results, not adapter internals.
    5. New infrastructure is introduced only when a milestone's proof requires it.
    6. Failures remain typed: poor task performance, invalid output, timeout, resource exhaustion, policy violation, and infrastructure failure are not interchangeable.
    7. Tests are deterministic by default. Tests requiring credentials, network access, or hardened infrastructure are explicitly separated.
    8. Each milestone updates examples, tests, and user-facing documentation together.
    9. The programming model is the canonical public API contract; other documents link to it rather than redefining signatures.
    10. Canonical examples are first-class user-facing documentation, not test fixtures: each must be short, copy-pasteable, and runnable from a clean checkout, and the simple callable path never requires or surfaces kernel vocabulary such as Trial, OperatorSpec, or WorkItem.

    Pre-milestone API spike

    Status: complete (July 16, 2026). Both demonstrations ran through the same small public surface under experiments/00_api_spike/, including a real gpt-5.4-mini Codex SDK prompt-optimization run. The exit gate passed: findings are recorded in real_model_findings.md and folded into the programming model's evidence section. Closed by #23.

    Goal

    Exercise the smallest declarative API before durable domain models and package boundaries are fixed.

    Demonstrations

    Build a disposable one-to-three-file implementation that runs:

    1. deterministic integer improvement with Greedy and BestOfN;
    2. one real-model prompt-optimization task whose proposer and evaluator each require only a small user function.

    The spike should test the canonical Task, meta.run, proposer, evaluator, search, and Run.best()/lineage() surface from the programming model.

    Questions it must answer

    • Can a plain callable be used as a proposer and evaluator in local mode?
    • Is the distinction between task, seed, proposer, evaluator, and search obvious in working code?
    • Does changing search policy require no change to task or proposer code?
    • Can failures and multi-metric evaluations be represented without exposing orchestration machinery?
    • Which values must become durable records, and which abstractions are premature?

    Exit gate

    • Both examples run through the same small public surface.
    • The programming model is revised from observed use rather than aspiration alone.
    • Any deliberately unsupported capability is named explicitly.
    • None of the spike's internal structure becomes a kernel contract without Milestone 1 justification.

    Out of scope

    Replay, crash recovery, ports and adapters, stable schemas, experience grants, workspace isolation, provider portability, and production-quality model integration.

    Common definition of done

    A milestone is complete only when:

    • its canonical example runs from a clean checkout;
    • its acceptance tests pass locally and in CI where the required capabilities are available;
    • events, artifacts, evaluations, and policy decisions retain causal lineage;
    • public contracts and durable schemas are documented and versioned;
    • newly added adapters pass their conformance suites;
    • resource use and failure outcomes are observable;
    • no later-milestone infrastructure was added speculatively;
    • the next milestone can build on the result without replacing the kernel.

    Release checkpoints

    Checkpoint Included milestones Meaning
    Kernel proof 1–3 The abstractions compose, policies are replaceable, and agents can reuse prior experience.
    Durable local engine 4–6 Runs persist, real code can execute, and one SDK agent works end to end.

    Evolution system 8–9 Harnesses and search policies can be evaluated as artifacts under external controls.

    Milestone 1: deterministic kernel

    Status: complete (July 21, 2026; #1, #32). The canonical number search, exact budget accounting, retained-event projection rebuild, built-in Greedy decision reproduction, failure replay, and the remaining acceptance tests now pass. Restart and resume were deliberately deferred to, and are now shipped by, Milestone 4.

    Goal

    Prove the smallest complete improvement loop without language models, subprocesses, databases, or distributed workers.

    Canonical demonstration

    An integer artifact begins away from a hidden target. Deterministic proposers add or subtract fixed values, a pure evaluator rewards proximity to the target, and a sequential coordinator runs until its evaluation budget is exhausted or the target is reached.

    select parent
  → allocate bounded work
  → produce proposal
  → create successor artifact
  → evaluate with evidence
  → append events
  → update projected state
  → choose the next action

    Deliverables

    • Frozen, serializable domain models for tasks, artifacts, proposals, trials, trial outcomes, evaluations, evidence, budgets, usage, policies, and typed events; a work-item delivery record stays internal to the kernel and out of user-facing types.
    • Opaque typed identifiers and schema versions on durable envelopes.
    • In-memory artifact and event stores.
    • A deterministic callable proposer adapter and pure-function evaluator adapter.
    • A sequential coordinator that validates transitions, authority, and budgets.
    • A minimal SearchProgram.next(state) decision contract; remaining budget is part of projected state.
    • Typed OperatorSpec values produced by operator policies rather than durable raw strings.
    • Logical ordering, deterministic tie-breaking, and recorded named random substreams.
    • examples/01_number_search/ with a documented run command.

    Expected behavior

    • The same task, initial artifact, policy, seed, and budget produce the same logical decisions and final projected state.
    • Every artifact and evaluation can be traced to the trial, proposal, and search decision that caused it.
    • Trial identity remains distinct from duplicate delivery or completion attempts.
    • Duplicate completion is idempotent.
    • Exhausted budgets prevent additional work.
    • Invalid proposals and evaluator failures are recorded without being treated as low scores.
    • The run can be rebuilt from its event stream without agent-local state.

    Acceptance tests

    • Reachable and unreachable target scenarios.
    • Exact evaluation and usage accounting.
    • Deterministic replay from an empty projection.
    • Decision reproduction with the same named random substreams and trial seeds.
    • Optimistic append conflict in the in-memory event store.
    • Duplicate work completion.
    • Invalid transition and budget-exhaustion rejection.
    • Failure taxonomy serialization and replay.

    Out of scope

    SQLite, filesystem persistence, subprocesses, real agents, semantic search, snapshots, concurrency, and user interfaces beyond the example command.

    Milestone 2: replaceable search policies

    Status: complete. M1 supplies the Greedy baseline and the generic preparation boundary. M2.1 adds durable archive decisions, linked decision explanations, and the first reusable policy-contract gate. M2.2 adds the public BestOfN(max_trials=20) preset, independent seed expansion, and historical decision reproduction through the same contract. M2.3 adds the public Population(size=3, tournament_size=2, max_trials=20) preset with explicit rank-ordered archive membership, deterministic tournament selection, and a corridor test showing retention of a temporarily worse branch. M2.4 adds strict compatible-run comparison and the canonical equal-budget three-policy benchmark.

    Goal

    Prove that search behavior is a replaceable policy and that different policies can be compared fairly without changing the coordinator.

    Canonical demonstration

    Run independent best-of-N, greedy hill climbing, and a small population policy against the same integer task, initial artifact, seed rules, and evaluation budget. Produce a comparison report containing best score, evaluations, usage, and lineage references.

    Deliverables

    • Independent best-of-N policy.
    • The M1 Greedy baseline covered by the shared M2 policy conformance suite.
    • Small population retention policy.
    • Deterministic selection and tie-breaking rules.
    • Explicit admission, stopping, and budget-allocation decisions.
    • A run-comparison projection or report.
    • One publishable benchmark example: an honest, reproducible equal-budget comparison (for example, greedy with context reuse versus independent best-of-N) presented as a notebook or report a reader can rerun, serving as the project's first credibility artifact.
    • examples/02_policy_comparison/.

    Expected behavior

    • Policies consume the same projected state and return typed decisions.
    • Replacing a policy requires no coordinator, runtime, evaluator, or storage changes.
    • Every policy decision records its inputs, policy version, rationale metadata, and observed logical step.
    • Comparisons normalize results by the same declared budget.
    • A policy cannot directly mutate projections or grant itself additional budget.

    Acceptance tests

    • All three policies pass one shared policy conformance suite.
    • Equal inputs produce deterministic decisions.
    • Tie cases have stable outcomes.
    • Population admission and eviction replay correctly.
    • A historical policy decision can be reproduced without future evaluations.
    • Adding a minimal test policy requires only implementing the policy contract.

    Out of scope

    Pareto archives, novelty search, islands, bandits, MCTS, learned allocation, and policy evolution.

    M2.4 completion

    Run.summary() and Run.compare() are immutable derived views over committed records. Fair comparison requires identical evaluator/proposer declarations, primary objective, task and effective run budgets, artifact kind, and initial artifact declaration and digest. Policy choice, policy configuration, and root seed may differ; exact primary scores tie without a usage or policy tiebreaker.

    The canonical examples/02_policy_comparison/ sweep uses target 12, moves (-2, 1, 5), initial value 0, nine evaluations, eight successor trials, and root seeds 0 through 39. Its executed notebook reports complete score and usage distributions and representative star, chain, and tree-branch lineages, with an explicit small-illustration evidence disclaimer. The companion executed milestone_2_tour.ipynb introduces M2.1 through M2.4 from the public callable path before showing optional kernel-level inspection.

    Milestone 3: shared experience and agent-directed exploration

    Status: complete (July 24, 2026; #3). M3.1 adds the read-only temporal experience projection, M3.2 adds bounded replayable policy-pushed context, M3.3 adds audited, strictly-prior agent-pulled access, and M3.4 adds declared derivation, run-aggregate experience usage, memory-strategy comparison, and the canonical four-variant demonstration.

    Goal

    Make prior trials useful to later agents through both policy-pushed context and agent-pulled investigation.

    Canonical demonstration

    Agent A produces several failed trials. Agent B searches those trials, opens a relevant proposal and evaluation, compares siblings, and uses the observed failure to choose a successful transformation. The new proposal records the exact experience B observed and used.

    Deliverables

    • An in-memory ExperienceGraph projection with occurrence-based node, ancestor, child, inclusive-sibling, causal-leaf frontier, trace, and inclusive historical state_at queries.
    • A scoped, read-only ExperienceReader with exact filtering and traversal.
    • ExperienceGrant bounds for task, run, logical time, result count, context size, and resource use; identity and visibility remain single-user stubs.
    • ContextPolicy implementations for NoMemory, AncestorsOnly, and BestSibling.
    • Events for automatic context selection, experience queries, opened records, and comparisons.
    • Immutable ContextBundle records and exact query-result records, including ordering and truncation.
    • Stable references from observed experience into Proposal.derived_from.
    • examples/03_experience_reuse/ covering push-only, pull-only, and combined access.

    Expected behavior

    • Agents distinguish experience that existed from experience they actually observed.
    • An as_of argument may narrow but never widen a work item's logical-time grant.
    • Cross-task, out-of-run, retracted, or future experience is not returned.
    • M3.2 context selection obeys record and rendering bounds without consuming task usage; M3.3 pull operations count against their ExperienceGrant.
    • The derivation graph remains acyclic while semantic relationships may be typed cross-links.
    • Content deduplication does not collapse distinct causal occurrences.

    Acceptance tests

    • Agent B improves by consulting Agent A's recorded failure.
    • Push-only, pull-only, combined, and no-memory variants run under equal budgets.
    • Ancestor, sibling, and historical-state queries return expected results.
    • Attempts to cross task, run, or logical-time boundaries fail.
    • Query result limits and usage limits are enforced.
    • Replay reconstructs the same observed-context references and derived-from edges.

    Out of scope

    Embeddings, vector databases, learned retrieval, graph databases, filesystem projections, principal-based authorization, licensing enforcement, and cross-installation experience.

    M3.1 completion

    replay_experience_graph() derives one trial-centered node per committed trial occurrence through the validated run replay path. ExperienceRef uses the run, record kind, and existing occurrence identity; identical artifact payloads therefore remain distinct causal occurrences. Exact decision, explanation, proposal, artifact-creation, outcome, evidence, evaluation, and completed-trial records are retained without defining another lifecycle.

    Queries are scoped by task, run, and an optional inclusive logical step. Ancestors exclude self, siblings include self, frontier means visible causal leaves rather than archive membership, and a trace spans the target trial and its accessible ancestors while preserving committed event order with a fixed intra-event kind order. Missing, wrong-kind, cross-scope, future, hidden, retracted, and synthetic non-local direct targets all receive one opaque denial. Collection reads omit inaccessible occurrences and do not traverse through them.

    Only ExperienceRef is durable and exported through meta_evolve.domain. Graph and query views remain outside the package-root callable API. M3.1 adds no reader grant, pushed context, retrieval, durable graph store, authentication, licensing, or proposal-derivation contract.

    M3.2 completion

    meta.run(context=...) accepts NoMemory, AncestorsOnly, BestSibling, or a compatible declared policy. None and NoMemory() preserve pre-M3.2 identity, stream, trial specs, and proposer behavior except that the internal ProposerContext now exposes a synthesized empty bundle. Non-default configuration contributes one final serialized ContextSpec identity segment.

    ContextPolicyDeclared follows bootstrap evaluation. A transparent search-program wrapper stamps its policy reference only into successor specs, and a generic coordinator operation commits one ContextSelected after the decision explanation and before proposer invocation. Bundles snapshot exact typed records, stable reference order, canonical rendering, reason, truncation, and ContextUsage; record and character bounds are independent from task Usage.

    AncestorsOnly flattens accessible ancestors in graph-node and committed-record order. BestSibling excludes the current node, ranks only successful sibling evaluations through rank_evaluations, and preserves completion-order ties. Replay validates the committed records against their strictly prior visible sources and returns the committed bundle without rerunning selection or rendering. Context declaration and selection facts remain inspectable in the experience graph but cannot themselves become policy candidates.

    M3.3 completion

    meta.run(experience=...) accepts the run-level ExperienceAccess protocol; PullAccess(max_operations=20, max_results=20, max_records=100, max_chars=32_000) is the shipped declaration. None normalizes completely away. A non-default access declaration contributes the final serialized ExperienceSpec identity segment after any ContextSpec.

    Every successor receives a fresh immutable ExperienceGrant bounded to the same task/run and as_of=trial.logical_step - 1. Its ExperienceReader supports exact conjunctive search filters, open, ancestors, inclusive siblings, and right-minus-left numeric comparison. Results preserve committed ordering, exact structured snapshots, canonical prefix-bounded rendering, truncation, and cumulative operation/result/record/character usage. Failed evaluations remain inspectable and never become synthetic losses.

    The audited lifecycle is grant → (attempt → success|denial|exhaustion)* → proposal. Attempts charge before validation, opaque denials disclose no protected content, and over-ceiling calls receive a separate content-free exception. Replay validates authority, placement, reproducible operation identities, cumulative charging, and terminal matching, and holds every success to the shared deterministic contract: records must equal committed sources inside the effective boundary, references must stay visible, deltas must derive from the paired records, and rendering must prefix the canonical rendering of the committed records. Selection, traversal, filtering, and comparison logic is never re-run, and committed outcomes are returned directly. Context and pull-audit facts remain graph-inspectable but are excluded from both push and pull candidate sets, and naming them in a search filter is a malformed request. Pull usage does not change task budgets, logical steps, or named randomness.

    M3.4 completion

    Proposal and callable ProposalResult now carry an explicit ordered derived_from declaration. One shared pure validator reconstructs pushed and pulled observations from committed records and requires a unique, strictly-prior same-run subsequence. Resource exhaustion precedes derivation policy failure; both coordinator-imposed failures clear edges and commit no candidate. Valid typed proposer failures and failed independent evaluations retain their declared lineage.

    Canonical serialization omits empty derivation and rejects an explicitly encoded empty default, so old proposal, event, context, and replay bytes remain unchanged at schema version 1. RunExperienceUsage, Run.experience_usage(), and expanded summaries report context and pull totals. Comparisons continue to require equal task/run budgets and core declarations while allowing different memory strategies, with exact declaration-match flags.

    The runnable examples/03_experience_reuse/ experiment gives no-memory, push-only, pull-only, and combined variants the same task, proposer, evaluator, chain search, seed, and task/run budget. It records early evaluator failures, then succeeds only when prior failure evidence is reused and cited. Replay reconstructs the same derivation edges. The companion executed milestone_3_tour.ipynb introduces M3.1 through M3.4 from the public callable path, with push_pull_lab.ipynb and derivation_comparison_lab.ipynb as focused kernel-level labs.

    Milestone 4: durable local runs and crash recovery

    Status: complete (July 24, 2026; #4, #47). Durable artifacts and events, atomic commit, verified manifests, corruption detection, migration, recovery-frontier replay, and context/experience-aware resume satisfy the acceptance gate without changing the M1–M3 logical identities or trajectories.

    Goal

    Persist the kernel without changing its logical behavior and prove that interrupted runs resume safely.

    Canonical demonstration

    Start a deterministic run, complete several trials, terminate the process, rebuild the coordinator and projections from disk, resume from the committed frontier, and compare the outcome with an uninterrupted run.

    Deliverables

    • SQLite append-only event store with optimistic concurrency.
    • Content-addressed filesystem artifact store.
    • Durable run, trial, population, work-item, usage, and experience projections.
    • Stable idempotency keys and committed logical steps.
    • A resume command or documented API.
    • Migration/versioning strategy for durable schemas.
    • examples/04_crash_recovery/.

    Expected behavior

    • SQLite and in-memory adapters satisfy the same event-store contract.
    • Identical payload bytes reuse content identity while occurrence provenance remains distinct.
    • Only atomically committed object records and transition events affect reconstructed state.
    • Restarting does not repeat completed logical work or lose remaining budget.
    • Historical state is initially reconstructed from immutable object records and transition events; snapshots are optional future caches.
    • Corrupt or incompatible durable data fails explicitly rather than being silently ignored.

    Acceptance tests

    • Interrupted and uninterrupted deterministic runs reach equivalent logical results.
    • Restart before and after each important transition.
    • Duplicate completion across a restart.
    • Optimistic concurrency conflicts across two store clients.
    • Artifact deduplication with distinct causal occurrences.
    • Projection rebuild from empty projection tables using durable object records and transition events.
    • Durable schema-version rejection and supported migration tests.

    Out of scope

    Graph databases, remote databases, object stores, parallel workers, filesystem snapshots, and backup services.

    Milestone 5: executable artifacts and external evaluation

    Status: complete (July 24, 2026). M5.4 closes the canonical script, executed notebook, integrated acceptance, durable-query, and documentation gates without adding a production API or widening the development sandbox.

    Goal

    Safely enough for development, execute candidate source artifacts in private workspaces while keeping evaluation outside candidate authority.

    Canonical demonstration

    A deterministic patch agent improves a small Python function. Each candidate is materialized into its own workspace and evaluated by external unit tests that the candidate cannot modify.

    Deliverables

    • [x] Immutable SourceTree with stable utf8-tree-v1 digesting.
    • [x] Synchronous directory-copy WorkspaceProvider for materialize, capture, and dispose.
    • [x] Exact-file TextPatch, rich PatchResult, and workspace-backed PatchProposer.
    • [x] Generic ProposerRunner seam preserving the decoded callable path.
    • [x] Clearly named development subprocess SandboxProvider with timeouts and captured output.
    • [x] External evaluator adapter with versioned environment and evidence.
    • [x] Typed process outcomes for success, timeout, resource exhaustion, policy violation, infrastructure failure, and task failure.
    • [x] examples/05_python_function/.
    • [x] Executed milestone_5_tour.ipynb with deterministic semantic output.

    Expected behavior

    • Every work item receives a private writable workspace derived from an immutable parent.
    • Capturing changes produces a new immutable artifact without altering its parent.
    • Evaluator code and hidden tests remain outside the candidate mutation boundary.
    • Process execution and task evaluation failures remain distinguishable.
    • Workspace cleanup runs after success and failure.
    • Durable local history remains queryable, while cold resume of local workspace components fails explicitly with CapabilityError.
    • The subprocess adapter makes no claim to safely execute untrusted community code.

    Acceptance tests

    • Passing, failing, invalid, and unchanged patches.
    • Parent immutability after workspace capture.
    • Timeout and process-output capture.
    • Workspace cleanup after evaluator or runtime failure.
    • Candidate attempts to modify external evaluator inputs.
    • Stable source-tree digests and artifact round trips.
    • Workspace and sandbox adapter conformance suites.

    The acceptance suite pins the broken and repaired content digests, scores 0 → 1, process exits 1 → 0, evidence kinds, winning lineage, reopened best/lineage equivalence, clean-checkout script output, and temporary notebook re-execution. It also proves a failed cold resume leaves events, artifacts, and both workspace trees unchanged. The exact development boundary is unchanged: patch traversal is rejected, capture excludes the grader, and the canonical run leaves grader bytes intact; hostile-runtime filesystem isolation is not claimed.

    Out of scope

    Containers, hardened untrusted execution, Git worktree optimization, remote volumes, real LLM agents, multi-repository artifacts, and portable runtime reconstruction.

    Milestone 6: SDK proposer boundary proof

    Status: Shipped. M6 completed on July 28, 2026. It proved that native coding SDKs could produce ordinary candidates through the existing proposer seam without adding provider vocabulary or branches to the coordinator.

    The first-party Claude and Codex adapters, package extras, and provider-specific capture fixtures were superseded before 1.0 by the smaller user-owned SDK boundary and have now been removed. Their detailed implementation and live measurements remain available in Git history and closed issues #57–#93, but they are not part of the current source tree or acceptance surface.

    Shipped outcome

    • Plain callables and structural propose(parent, context) objects share one runner, preflight, accounting, evidence, and failure path.
    • ProposerContext exposes exact candidate-visible context and optional audited experience without task authority.
    • User code owns SDK authentication, sessions, tools, permissions, retries, output decoding, and provider telemetry.
    • Meta-Evolve owns candidate validation, independent evaluation, budgets, durable lineage, experience auditing, and promotion authority.
    • No provider dependency, extra, compatibility shim, generic provider runtime, or provider-specific coordinator behavior ships.

    Acceptance boundary

    Current deterministic tests prove the structural callable seam, configured component identity, typed SDK-wrapper failures, usage validation, pushed context, audited pull delegation, and declared derivation. Provider behavior is validated only by an explicitly authorized milestone-owned experiment when a current acceptance gate requires it.

    Out of scope

    A first-party provider adapter, cross-provider option model, generic agent runtime, durable provider session, automatic retry, portable live component reconstruction, or provider parity claim.

    Milestone 7: generality proof and local v1

    Historical annotation. M7's provider-conformance references describe the then-shipped M6 adapters. They were superseded by the user-owned callable boundary on August 5, 2026; M7's artifact-domain and local-kernel acceptance evidence remains current.

    Status: complete (August 2, 2026; #7, PRs #94–#97). Four artifact domains — number, text, repository, and skill set — reach the coordinator through one meta.run call site and leave an identical kernel record, with four distinct kinds over three representations (tests/test_four_domain_kernel.py). No domain needed a coordinator branch, and the proving phase changed no file under src/. A static gate holds the property open: application modules import no concrete adapter outside a justified wiring allowlist, and nothing dispatches on a concrete artifact type outside the codecs and the adapters (tests/test_application_purity.py). The add-a-domain walkthrough is docs/adding-an-artifact-domain.md; its code blocks are one script, executed in a fresh interpreter from an empty directory and compared against the output the page claims, so the documentation walkthrough cannot drift from the library.

    Three deliverables landed differently from their wording above, and the difference is not absorbed into it:

    • Extension contracts. M7 added the ArtifactCodec contract and the optional RunIndex capability, and changed ProposalResult to carry an artifact value rather than a frozen payload. The runtime, evaluator, workspace, and sandbox ports and the search- and context-policy contracts already existed and gained no members here.
    • Commands. The command line ships five verbs, not four: list joins run, inspect, resume, and compare. Run ids are content-derived digests rather than names anyone retypes from memory, so without enumeration every other verb becomes unreachable once an id leaves the terminal. It rests on one new read-only storage surface, Storage.runs().
    • Conformance utilities cover two of the seven component types. meta_evolve.conformance publishes suites for artifact codecs and for repository-editing proposers. Search policies, workspaces, and sandboxes keep reusable function-based suites under tests/ that were not published; evaluators and context policies have concrete tests and no reusable suite at all. An extension author writing any of those five has nothing to subclass. Publishing the rest is additive and remains open, tracked in #98. M8 evaluates harnesses under external control, so it is the first milestone likely to need a published evaluator or policy suite.

    The defect-repair pass (July 30 – August 2, 2026)

    Building examples 07–17 and hardening their reopening path exposed six defects in M7's own deliverables. Each is backed by something that actually broke while measuring, not by review speculation, and three of them turned real measurements into misleading ones. They are recorded here rather than deferred because a milestone that ships a misleading measurement has not met its own acceptance gate.

    defect what it cost closed by
    No public accessor for a losing attempt six examples reached into run._projection() or inferred failure from evaluation_count; two invented "no candidate" as a reason for what was really a timeout Run.trials() and TrialView.state
    A missing extra became a per-candidate score a CapabilityError in an evaluator surfaced as NoSuccessfulEvaluation, blaming the candidate for the machine CapabilityError reserved as abort control flow at both boundaries
    A hardcoded turn limit measured itself three corrupted measurements, including an A/B that lost 7 of 8 control reps Claude(max_turns=…, pull_max_turns=…)
    compare could not see a model inside an evaluator closure a winner reported for an uncontrolled comparison name_only_components reports it; ComponentRef.configured_local lets a caller close it

    A stored custom-domain local run could not be decoded after restart durable storage outlived the live codec index, but Run(id, storage) knew built-ins only keyword-only Run(..., registry=...) reconstructs the read-only codec index without granting execution authority

    Reopening a closed milestone sets a precedent, so the justification is narrow and stated rather than assumed. These are repairs to M7's own shipped surface, found by M7's own acceptance examples, and they add no milestone scope. The passage below about Pi integration and filesystem-shaped experience is not a general convention authorizing this — it is specific to those two post-M6 follow-ups. Anything that is genuinely new capability belongs in M8.

    Two things this pass deliberately did not do. It did not raise either turn limit: the defaults emit byte-identical native profiles, so a run recorded before the pass still replays. That statement is about the library's defaults only. Any run that declares a turn ceiling declares a different component, and its component.version and RunId move accordingly — which is correct, and is why compare refuses two runs whose ceilings differ. Examples 12, 15, 16 and 17 all declare one, so all four moved; example 17's evaluator identity moved for a second, independent reason. And it did not make compare infer a configuration it was never told about — compare still refuses only on what a run declared, which is why the gap is reported as well as made closeable.

    One tightening in the same pass is not a defect repair, so it is recorded apart from the table. Registry.register_artifact_type now refuses a kind, representation, or declared interface name that is empty or carries outer whitespace, through the same _require_text the rest of the domain uses. An empty interfaces tuple stays valid and means the codec declares no consumer-facing interface. These fields reach durable records and content-derived ids, so registration refuses a bad declaration rather than normalizing it — a silently trimmed kind would encode artifacts under a name its own author never wrote. The observable change for an extension author is the exception type: a non-string kind raised TypeError before this pass and raises ValueError now, so declaration validity is one error family instead of two.

    Goal

    Demonstrate that the kernel is a reusable framework rather than an implementation specialized for one artifact or task domain.

    Canonical demonstrations

    Run four use cases through the same coordinator:

    1. deterministic number search;
    2. text or prompt optimization;
    3. repository/code improvement;
    4. skill-set evolution.

    Only artifact codecs, task definitions, proposers, evaluators, and policy configuration may differ between the examples.

    Deliverables

    • Public extension contracts for artifact codecs, runtimes, evaluators, search policies, context policies, workspaces, and sandboxes.
    • A small artifact-type registry with schema validation and declared interfaces.
    • Text/prompt and skill-set artifact implementations.
    • Minimal user-facing API and commands to run, inspect, resume, and compare experiments.
    • Adapter conformance-test utilities for extension authors.
    • A concise tutorial for adding a new artifact domain.
    • examples/07_text_optimization/ and examples/08_skill_evolution/.

    Expected behavior

    • No coordinator branch checks a concrete artifact type, provider, evaluator, or policy.
    • A new domain is added by registering implementations behind existing contracts.
    • All examples expose comparable lineage, budgets, evaluations, and experience views.
    • Users can inspect why a candidate exists, what an agent observed, and why it was evaluated or admitted.
    • A clean local installation can run deterministic examples without provider credentials.
    • Provider-dependent examples fail with actionable setup guidance.

    Acceptance tests

    • Run all four domains through one shared kernel test harness.
    • Static or behavioral check that the coordinator imports no concrete adapters or artifact implementations.
    • Create a minimal custom artifact/evaluator in a test without modifying core packages.
    • Public API serialization and schema-version tests.
    • CLI smoke tests for run, inspect, resume, and compare.
    • Documentation walkthrough from a clean environment.

    Exit gate

    If a use case requires a domain-specific coordinator branch, stop and repair the abstraction before beginning harness evolution. Passing this gate defines the local v1 architecture.

    Out of scope

    Complete harness mutation, policy evolution, concurrency, remote workers, federation, dashboards, and plugin marketplaces.

    Pi integration and filesystem-shaped experience are post-M6 follow-ups. They do not retroactively widen M6's portability or conformance gate and enter M7 only through separately accepted issues.

    Goal

    Treat an executable agent harness as a typed composite artifact whose permitted components can be improved under external evaluation and promotion controls.

    Canonical demonstration

    A worker harness performs held-out tasks. An outer agent investigates earlier harness source and traces, then modifies one or two declared surfaces—initially a planner prompt and context policy. External evaluation determines whether the successor is admitted.

    The outer agent is injected as a user-owned callable. CI uses a deterministic fixture-backed SDK client; an opt-in maintainer driver may call a real SDK through the same boundary. The first authorized live run is captured once, sanitized, and retained with ties, regressions, and failures intact. Evaluation, equal budgets, mutation authority, and promotion stay outside the wrapper. See the boundary decision.

    Deliverables

    • HarnessArtifact manifest containing component references and declared interfaces.
    • Typed parameters for initial mutable surfaces such as TextParam and PolicyParam.
    • Explicit MutationSurface separating candidate-controlled components from hidden evaluation, secrets, permissions, budgets, audit history, and promotion policy.
    • Harness materialization, execution, capture, and validation.
    • Held-out task split and promotion rule.
    • Harness-specific comparison views over quality, cost, and failure behavior.
    • examples/20_harness_evolution/.

    Expected behavior

    • A candidate can modify only manifest-declared mutable surfaces.
    • Component references and the composite harness both retain content identity and causal lineage.
    • Harness evaluation runs fresh executions rather than trusting self-reported improvements.
    • Failed or invalid harnesses remain inspectable experience.
    • Later agents can compare complete harness code and traces, not only summary feedback.
    • Additional mutation surfaces can be registered without changing the coordinator.

    Acceptance tests

    • Valid prompt and context-policy mutations.
    • Rejection of hidden-evaluator, permission, budget, and promotion-policy changes.
    • Composite artifact digest and provenance tests.
    • Fresh held-out evaluation and deterministic fixture tests.
    • Comparison against the unchanged baseline harness under equal budgets.
    • Resume and replay of a harness-evolution run.

    Out of scope

    All mutation surfaces at once, unrestricted self-modification, automatic promotion to production, policy meta-evolution, and claims of general recursive self-improvement.

    Milestone 9: policy artifacts and meta-evolution

    Status: Shipped (August 6, 2026). The canonical deterministic example is examples/21_policy_evolution/. M9 depends on the contracts shipped in M8.1–M8.5; it does not depend on #124 or the still-open M8.6 live proof.

    Executable subissue program

    • [x] M9.0: lock dependency, authority, reuse, aggregation, and namespace decisions before implementation.
    • [x] M9.1: ship search-policy / policy-manifest-v1, two fixed mutation surfaces, neutral mutation contracts, and four-surface conformance.
    • [x] M9.2: register trusted candidate-policy@1, publish SearchProgramTests, and verify durable reconstruction.
    • [x] M9.3: ship portable policy episodes, explicit splits, captured inner run references, exact reuse/resume boundaries, and nested usage separation.
    • [x] M9.4: aggregate all outcomes and strictly compare separate seed-only held-out outer runs without granting promotion authority.
    • [x] M9.5: run the deterministic durable flagship with development quality 6.0 → 7.0 → 8.0 and held-out aggregate 13.5 → 15.5.

    M9.0 executable contract

    • meta_evolve.policy owns artifact-domain values; meta_evolve.policies continues to own executable presets.
    • Only generic MutationApplication[SurfaceT] and MutationSurface[MutationT, SurfaceT] move to meta_evolve.mutation; harness-specific mutations and parameters stay namespaced under harness.
    • Policy episodes and comparisons remain domain-specific peers of harness equivalents. No generic episode/comparison framework exists without a third domain demonstrating it.
    • An episode's existing content-addressed RunId is its sole cache identity. Aggregates are recomputed; evaluator identity covers the exact suite, split, scoring, aggregation, budgets, and environment.
    • Fresh development forbids non-identical reuse, while an exact completed run may reopen. Held-out execution always uses a new empty namespace and bypasses reuse.
    • Any failed, incomplete, or missing episode makes the aggregate non-rankable while retaining partial results and typed failures.
    • Inner trials and evaluations remain inner usage. Only tokens and elapsed time roll into the enclosing evaluation's Usage.
    • Candidates cannot control tasks, seeds, proposers, evaluators, environments, budgets, split membership, caching, aggregation, promotion, or executable policy source.

    Goal

    Evaluate search or update policies as artifacts by measuring the improvement episodes they produce on held-out task distributions.

    Canonical demonstration

    Two versioned PolicyArtifacts each control fresh inner-loop optimization episodes across training and held-out tasks. An outer policy compares their quality, cost, robustness, and failure rates under equal nested budgets.

    Deliverables

    • Serializable PolicyArtifact with declared interfaces and mutation boundaries.
    • Nested run/episode relationships and separate inner/outer budgets.
    • Task-distribution artifacts and held-out evaluation splits.
    • Existing RunId cache identity and explicit leakage boundaries.
    • Aggregation of quality, cost, uncertainty, and failure metrics across episodes.
    • External promotion decision for policy candidates.
    • examples/21_policy_evolution/.

    Expected behavior

    • A policy candidate cannot inspect held-out results before its evaluation episode permits them.
    • Inner-loop events retain their own lineage while linking to the outer policy evaluation.
    • Cache hits are valid only when task, artifact, policy, evaluator, environment, seed, and relevant budget semantics match.
    • Promotion uses fresh evidence across multiple tasks or seeds rather than a policy's self-report.
    • Budget exhaustion in an inner episode does not consume undeclared outer authority.

    Acceptance tests

    • Compare two deterministic policy artifacts across several task fixtures.
    • Nested budget accounting and exhaustion.
    • Held-out leakage rejection.
    • Cache-key correctness and invalidation.
    • Episode aggregation with failed and incomplete runs.
    • Replay from an outer decision to every supporting inner evaluation.

    Out of scope

    Learned schedulers, model-weight training inside the kernel, autonomous authority changes, production deployment, and claims that improvement generalizes beyond measured tasks.

    Milestone 10: trusted concurrency and distribution

    Goal

    Execute work concurrently on trusted workers without corrupting history, budgets, population state, or promotion decisions.

    Canonical demonstration

    Several worker processes claim bounded work through leases. Workers finish out of wall-clock order, one lease expires, and one result is submitted twice. The reconstructed logical run preserves one trial across delivery retries, contains one accepted outcome, and has correct budget accounting.

    Deliverables

    • Durable work states and atomic lease acquisition, renewal, expiration, cancellation, and completion.
    • WorkAttempt identities that remain distinct from their logical Trial and WorkItem.
    • Worker capability and resource declarations.
    • Idempotent result submission and retry policy.
    • Atomic budget reservation and settlement.
    • Scheduler matching work requirements to trusted workers.
    • Explicit consistency rules for durable facts, leases, heuristic frontier statistics, and promotion.
    • Multi-process load and fault-injection test harness.
    • examples/22_trusted_workers/.

    Expected behavior

    • At most one completion has logical effect for an idempotency key.
    • Expired workers cannot overwrite an accepted result.
    • Out-of-order completion does not create future-information leakage.
    • Durable events and evaluations are strongly inserted; heuristic statistics may tolerate documented staleness.
    • Promotion and budget accounting use authoritative state.
    • Local and distributed runs preserve the same task, artifact, trial, work, evaluation, and event semantics.

    Acceptance tests

    • Competing lease claims.
    • Lease renewal and expiration races.
    • Duplicate and late result submission.
    • Worker termination during execution and evaluation.
    • Atomic budget reservation under concurrency.
    • Projection rebuild after out-of-order events.
    • Load test with simulated trusted workers before paid agent fleets.

    Out of scope

    Arbitrary untrusted community code, Byzantine workers, public federation, reputation economies, and universal strong consistency.

    Milestone 11: contributed and federated network

    Goal

    Allow independent installations to contribute and exchange authorized agents, evaluators, artifacts, evidence, and experience subgraphs with verifiable provenance.

    Canonical demonstration

    Two Meta-Evolve installations exchange a signed, policy-filtered experience bundle. The receiving installation verifies identity and content, imports only authorized records, preserves source provenance and restrictions, independently evaluates a promoted candidate, and processes a later retraction.

    Deliverables

    • Signed manifests for contributors, agents, evaluators, tasks, environments, and artifact schemas.
    • Scoped identities and task-specific trust policies.
    • Canonical export/import format for policy-filtered experience subgraphs.
    • Verification of signatures, content digests, schema compatibility, causal closure, and access labels.
    • Provenance, licensing, embargo, attribution, and retraction propagation through derivation edges.
    • Independent or redundant evaluation for promotion-sensitive results.
    • Minimal dispute and reputation projections based on recorded evidence.
    • examples/23_federated_exchange/ using two local installations.

    Expected behavior

    • Import never grants broader access than the source export policy and receiving trust policy allow.
    • Missing private ancestors can be represented by verifiable redacted references without fabricating lineage.
    • Invalid signatures, digests, schemas, or causal references are rejected.
    • Imported evaluations are evidence, not automatic local promotion.
    • Retractions and permission changes identify dependent artifacts, datasets, skills, and checkpoints.
    • Operators may keep private events while publishing permitted claims and artifacts.

    Acceptance tests

    • Successful signed export/import between two installations.
    • Tampered payload, signature, digest, and causal-edge rejection.
    • Private, embargoed, and redacted source handling.
    • Conflicting evaluator results and independent verification.
    • Retraction propagation through derived records.
    • Duplicate import idempotency and schema-version negotiation.
    • Threat-model review covering code execution, evaluator collusion, poisoning, sybil behavior, reward hacking, and correlated replication.

    Out of scope

    Token economies, unrestricted peer-to-peer execution, global consensus, claims that containers alone secure untrusted code, and scientific validity without domain-governed evidence and replication.

    Architecture gate across all milestones

    The following test should remain true throughout development:

    new use case
  = artifact codec and schema
  + task and evaluator
  + agent or mutator
  + search/context configuration
  + optional infrastructure adapters

new use case
  ≠ coordinator branch
  ≠ new durable semantics
  ≠ bypassed authority boundary

    When a new domain does not fit, first determine whether it needs a general protocol capability or whether it lies outside evaluated artifact-improvement loops. The kernel should grow only for the former.
