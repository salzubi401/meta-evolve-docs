    Build an autoresearch loop with Meta-Evolve

    Status: Shipped.

    Suppose you already have an agent that can improve a solution. How would you test changes to the research procedure itself without letting that procedure change its own benchmark, budget, or promotion rule?

    This chapter builds the smallest complete answer. It runs offline in a fraction of a second, and you do not need to open the optional notebook to understand it.

    The design is inspired by Weco's AIDE² report. It borrows the report's inner-task/outer-researcher experimental shape with fixed cost and private selection. It does not reproduce AIDE² or provide evidence of recursive self-improvement.

    The result first

    Run this from the repository root:

    uv run python examples/19_autoresearch/main.py
    Output
    autoresearch teaching run: outer=(evaluations=3,trials=2) inner=(evaluations=5,trials=4)
recipe=(1,) public={'public-large': 0.14285714285714285, 'public-small': 0.3333333333333333} private_quality=0.180556
recipe=(1, 2) public={'public-large': 0.2, 'public-small': 1.0} private_quality=0.321429
recipe=(1, 2, 4) public={'public-large': 0.3333333333333333, 'public-small': 0.5} private_quality=0.600000
selected=(1, 2, 4)
held_out_baseline={'held-out-small': 0.16666666666666666, 'held-out-large': 0.09090909090909091}
held_out_selected={'held-out-small': 0.5, 'held-out-large': 0.14285714285714285}
promotion=none

    The selected recipe does better in this constructed example. That shows the wiring works; it is not a scientific result.

    Each trial retains only its public report as candidate-visible evidence:

    [
    (str(trial.artifact.value), tuple(item.kind for item in trial.evidence))
    for trial in result.trials()
    if trial.artifact is not None
]

    [('{"moves":[1]}', ('autoresearch-public-report',)),

    The two levels

    “Inner” and “outer” describe which thing is being improved:

    outer Meta-Evolve run
│
├─ artifact: a recipe for conducting inner research
├─ proposer: change that recipe once
├─ evaluator: measure the changed researcher under a fixed protocol
└─ search: retain a recipe only when private quality improves
       │
       ├─ inner run on public task A
       ├─ inner run on public task B
       ├─ inner run on private task A
       └─ inner run on private task B

after outer selection
├─ seed researcher on held-out tasks
├─ selected researcher on the same held-out tasks
└─ report the comparison; promote nothing

    An inner run improves an integer on a small black-box landscape. The candidate research recipe says which move sizes it may try. (1,) makes slow local progress. (1, 2, 4) can cover more distance under the same four-trial limit.

    The integer task is intentionally unimportant. In a real project, replace it with model training, a solver, a coding agent, or another measured research task. The outer contract stays the same.

    The five Meta-Evolve declarations

    The outer loop uses the ordinary public API:

    return meta.run(
    task=meta.Task(
        evaluator=evaluate_researcher,
        artifact=meta.Text,
        objectives=(meta.Maximize("private_quality"),),
        budget=OUTER_BUDGET,
    ),
    seed=SEED,
    proposer=propose_researcher,
    search=meta.Greedy(max_trials=OUTER_TRIALS),
    context=meta.AncestorsOnly(max_records=CONTEXT_RECORDS),
    budget=OUTER_BUDGET,
    random_seed=0,
)

    Read it as a sentence: Task fixes evaluation and limits; SEED is the starting recipe; propose_researcher proposes a successor; Greedy retains improvements; and AncestorsOnly supplies public reports from parent lineage.

    The coordinator records every candidate, score, proposal hypothesis, evidence reference, decision, usage total, and causal parent.

    The candidate-controlled surface

    The complete mutable artifact is tiny JSON:

    {"moves":[1,2,4]}

    decode permits only the moves key, one to four integer moves, and values between 1 and 8. An invalid recipe produces a typed InvalidOutput with no metric, so malformed output can never outrank a valid researcher.

    import meta_evolve as meta

outcome = lab["evaluate_researcher"](meta.Text('{"moves":[0]}'))
print("failure:", type(outcome.failure).__name__)
print("metrics:", dict(outcome.metrics))
    Output
    failure: InvalidOutput
metrics: {}

    Everything else is experiment-controlled:

    Control Owner
    Move recipe Candidate
    Public, private, and held-out tasks Evaluator
    Inner and outer budgets Experiment
    private_quality calculation Evaluator
    Greedy admission Search policy
    Whether a winner is deployed Governance / user

    This separation is the safety and validity mechanism. “Self-improvement” does not mean self-authorized evaluation or deployment.

    One candidate evaluation

    evaluate_researcher first validates the recipe. It then performs four inner runs under byte-identical declarations:

    public = score(researcher, PUBLIC_TASKS)
private = score(researcher, PRIVATE_TASKS)
return EvaluationResult(
    metrics={"private_quality": fmean(private.values())},
    evidence=(
        EvidenceDraft(
            kind=PUBLIC_REPORT,
            data={"scores": public, "inner_trials_per_task": INNER_TRIALS},
        ),
    ),
)

    Public per-task outcomes become inspectable evidence. Private task names, targets, and per-task outcomes are not placed in evidence. The outer search policy receives only their aggregate metric for selection.

    The deterministic proposer extracts only autoresearch-public-report records. Its ProposalResult.derived_from points to the report it used. This preserves the causal claim “this change was based on that observation.”

    Exact budget arithmetic

    The seed and two successors give the outer run:

    3 outer evaluations = 1 seed + 2 proposals
2 outer trials      = 2 proposals

    Each outer evaluation runs four benchmark tasks. Each task permits the seed plus four inner proposals:

    5 inner evaluations per task
× 4 tasks per outer evaluation
× 3 outer evaluations
= 60 inner evaluations used for selection at most

    After selection, the seed and winner each run on two held-out tasks:

    5 × 2 policies × 2 held-out tasks = 20 post-selection evaluations at most

    The nested runs own their own hard budgets. The outer budget counts outer candidate evaluations; it does not pretend that a nested benchmark call is one unit of physical work. A production setup should additionally aggregate token, GPU-hour, dollar, and wall-clock usage at the evaluator boundary.

    Why three task splits?

    The public tasks provide feedback for proposing the next researcher. The private tasks decide whether the proposal survives. Held-out tasks are touched only after the search has selected a winner.

    Split Candidate model may see details? Affects selection?
    Public Yes Indirectly, through proposals
    Private No Yes, through aggregate quality
    Held-out No during search No

    If the outer model sees private targets or per-task results, “private” is only a label. If held-out results influence another proposal, those tasks have become part of development and a new untouched suite is required.

    Replacing the deterministic proposer with an agent

    The deterministic proposer keeps CI credential-free. A model-backed wrapper should preserve this boundary:

    ProposerContext → allowlisted public evidence → private workspace
  → one bounded agent session → validated ProposalResult
  → derived_from references and usage

    Do not give the model raw outer context because it contains the aggregate private metric needed by trusted search. Build an allowlisted workspace. The prompt-optimization example shows how a callable outer proposer can run a bounded source-tree agent one level down and lift the result back into meta.Text.

    For a source-code researcher, change the artifact to meta.SourceTree, use an exact mutation allowlist, and evaluate each candidate in a fresh workspace. Keep benchmark source, credentials, permissions, and promotion controls outside that tree.

    What the comparison may claim

    This tiny example supports one narrow statement: under the declared toy tasks and equal inner budgets, the selected recipe has higher private and held-out quality than the seed.

    It does not establish real-domain autonomy, superiority to experts, statistical robustness, out-of-distribution generalization, accelerating improvement, reward-hacking safety, or readiness for automatic deployment.

    Those claims require larger protocols, repeated runs, fixed physical costs, external baselines, untouched tasks, and adversarial checks. Negative results, ties, typed failures, and rejected proposals must remain in the record.

    Relationship to M8

    This is a pre-M8 composition of shipped M7 pieces: meta.Text, nested meta.run, typed evidence and failures, lineage, budgets, and an ordinary search policy. It introduces no production harness type or runtime behavior.

    M8 remains the owner of HarnessArtifact, MutationSurface, portable episode suites, replay, and promotion. When M8 ships, update this example to use those contracts or retain it only as the explicitly small composition. See the M8 design capstone.

    Leakage and validity checklist

    Before adapting the pattern, answer these questions:

    1. Can candidate code read private task files, environment variables, grader output, or prior held-out results?
    2. Are baseline and candidate evaluated on exactly the same tasks, seeds, model identity, tool permissions, and physical budget?
    3. Can a candidate increase concurrency, retries, context, or model calls and thereby buy a better score?
    4. Are malformed output, timeout, policy violation, and infrastructure failure unrankable typed outcomes rather than zeros?
    5. Does every proposal identify the public evidence it actually used?
    6. Is held-out evaluation run once after selection and excluded from promotion unless promotion policy explicitly owns it?

    Change and predict

    Change INNER_TRIALS from 4 to 2, update INNER_BUDGET consistently, and predict which recipe wins before rerunning the example. Then ask whether the winner changed because its research strategy is generally better or because the experiment changed the resource regime.
