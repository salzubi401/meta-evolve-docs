    Nested evaluation

    Status: Shipped.

    Some artifacts cannot be judged by looking at them. A library of skill documents is good exactly when an agent that has read it behaves better — so measuring one candidate means installing it into an agent, running that agent on real tasks, and aggregating what happened. In Meta-Evolve that inner work is not a special mode: the evaluator of an outer run simply executes complete inner runs. This chapter shows one such nested loop end to end and needs no prior chapter.

    The scenario

    The outer artifact is a SkillSet — an immutable mapping of file paths to skill documents — and the seed is empty. The measuring suite holds two repository episodes, each an ordinary inner task: edit a small repository so it satisfies a private house convention (a version-tag format in one episode, a verbosity rule in the other). The fixture calls the episodes "held-out" in the sense that matters here: their answers are private conventions that cannot be inferred from the repositories, only supplied by a skill document.

    One outer evaluation therefore means: render the candidate's skills into an inner agent's instructions, run one inner improvement run per episode, check each produced repository with that episode's local checker, and aggregate. The outer search never sees inside the episodes — only the aggregate comes back.

    The program

    uv run python examples/08_skill_evolution/story.py
    Output
    candidate: skill set
input skills: []
held-out episodes: ['version', 'verbosity']
progression: 0.0 -> 0.5 -> 1.0
final solved: 1.0
final skills: ['skills/verbosity.md', 'skills/versioning.md']

    What just happened

    Line by line: the empty seed solves neither episode (0.0); adding one skill document solves half the suite (0.5); adding the second solves all of it (1.0), and the selected skill set holds both documents. The progression is a real gradient — each outer candidate measurably improved on its parent, which is what lets an outer search select honestly.

    The nesting has a strict shape:

    outer candidate SkillSet
  → trusted evaluator renders skills into agent instructions
  → one inner run edits each episode's repository
  → the episode's checker measures the produced repository
  → trusted aggregation returns one outer evaluation
  → outer search selects the next skill-set parent

    Accounting stays honest across the boundary. Each inner run owns its own trials and evaluations; those counts never inflate the outer run's. Only tokens and elapsed time reported by inner agents roll up into outer usage, and the outer kernel records exactly one trial and one evaluation per outer candidate. Failure stays honest too: an episode that cannot complete makes the whole suite evaluation a typed failure — an unfinished measurement is not a solved-score of zero.

    One discipline matters more as the pattern scales. Whatever feedback guides the proposer during search, a genuinely fresh held-out split must remain untouched until search is over — data that influenced any proposal can no longer validate the winner. And as everywhere in the library, selecting a winner grants nothing beyond the record: promotion is an external governance decision.

    One extension

    Add a second, fresh episode suite and re-evaluate only the seed and the selected winner under it, requiring every episode to complete before aggregation. The EvoSkill build pattern names the exact callables to replace for a real system. Then continue to Durability and trust, where runs survive being stopped.
