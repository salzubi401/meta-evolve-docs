    Meta-Harness precursor: improve a bounded local harness

    Optional executable companion: open the canonical notebook. The notebook is not required to follow this chapter.

    Pre-M8 teaching precursor

    This local lab is not the M8 API. M8 remains the sole owner of HarnessArtifact, MutationSurface, portable episode suites, replay, and promotion. Update or retire this lab when M8 ships. See the M8 design capstone.

    The concrete problems

    The diagnostic row asks:

    How many NBA players have scored 60 or more points in a regular season game since 2023?

    The mutator may inspect the baseline's attempt on that row. It does not see the unseen validation row, whose question asks how many current and former Real Madrid players appear in the latest Forbes top-ten highest-paid-athletes list.

    The experiment asks whether changing a planner and context policy after one diagnostic failure helps on that separate validation case.

    What “harness” means here

    The local harness is an ordinary shipped meta.SourceTree containing exactly two files:

    planner.md
context_policy.json

    The baseline is conceptually:

    planner.md
  Answer from supplied evidence. Prefer recent documents.
  Return only the short answer.

context_policy.json
  {"max_documents": 5, "order": "given"}

    planner.md controls how the solver reasons and formats its reply. context_policy.json controls how many documents enter the solver workspace. The order is fixed to given in this precursor.

    This is intentionally smaller than a production harness. There are no new runtime types, portable manifests, automatic replay, or promotion records.

    From Meta-Evolve principles to this algorithm

    This lab widens the artifact from one prompt to two coordinated files while keeping every control outside that tree:

    Role Concrete component Boundary it demonstrates
    Mutable artifact Ordinary immutable meta.SourceTree Planner and context policy can change together
    Diagnostic evaluator Baseline solver plus local exact grade Produces evidence about current harness behavior
    Proposer Mutator session over read-only prior source/evidence Suggests file replacements but cannot apply arbitrary paths
    Mutation guard apply_mutation() Enforces allowlist and JSON semantics before evaluation
    Validation evaluator Same unseen row for baseline and candidate Measures the intended harness difference fairly
    Comparison compare() over two Measurements Reports improvement, tie, regression, or unrankable failure
    Promotion Constant False outside the candidate A better score does not deploy anything

    The research algorithm is therefore only this composition:

    observe baseline on development evidence
  → propose a bounded source change
  → reject changes outside authority
  → evaluate parent and successor on untouched validation
  → report comparison without promotion

    Meta-Evolve already provides the versioned tree, session failures, evidence, usage, and evaluator identity. The precursor adds no coordinator behavior. Its domain code is a two-path allowlist, one JSON validator, document slicing, and an equal-arm comparison.

    How the two files affect solver execution

    _solve() is the only function that interprets the harness. It parses context_policy.json, takes the first max_documents in fixed given order, renders them into validation.md, and uses planner.md as the solver instructions:

    SourceTree.context_policy.json ──► number of visible documents
SourceTree.planner.md          ──► reasoning and answer instructions
public SolverCase             ──► validation.md

    This means a mutation has two understandable levers: change how the model is instructed, change how much evidence it receives, or change both. It cannot add a tool, swap a model, reorder documents, alter the grader, or spend more sessions because none of those controls are interpreted from the artifact.

    _mutation_request() materializes prior files under prior/, diagnostic measurement/answer/trace under evidence/, and the lifecycle warning under controls/. The paths are read-only evidence in the mutator's workspace. The returned files object is not trusted as a patch until apply_mutation() checks paths, UTF-8 strings, non-identity, and policy JSON.

    Only after that guard returns a new immutable tree are the two validation sessions authorized. Invalid mutation therefore cannot consume held-out evaluation or leave a partial successor.

    The four sessions

    baseline harness ──► diagnostic attempt
       │                    │
       │                    ▼
       │            source + score + trace
       │                    │
       │                    ▼
       │              mutation session
       │                    │
       ├──────────────┐     ▼
       ▼              ▼  candidate harness
baseline validation  candidate validation
       └──────────────┬───────────────┘
                      ▼
          equal-declaration comparison
    # Session Candidate-visible inputs Output
    1 Baseline diagnostic Baseline harness and diagnostic public case Structured answer, trace, usage or failure
    2 Harness mutator Complete prior source and diagnostic record Proposed file edits
    3 Baseline validation Baseline harness and unseen public validation case Structured answer
    4 Candidate validation Candidate harness and the same validation case Structured answer

    The mutator's read-only workspace materializes:

    • the complete prior planner.md and context_policy.json;
    • the diagnostic exact score;
    • the baseline's candidate answer or typed failure;
    • recorded tool-trace kinds;
    • the lifecycle and authority warning.

    It does not contain the validation case, evaluator answer, permission state, budget controls, audit history, or promotion decision.

    Mutation authority

    The structured mutation shape is:

    {
  "files": {
    "planner.md": "Complete replacement planner text",
    "context_policy.json": "{\"max_documents\": 10, \"order\": \"given\"}"
  }
}

    The local validator applies an exact allowlist:

    allowed
  planner.md
  context_policy.json

protected examples
  evaluation_data.json
  permissions.json
  budgets.json
  audit_history.jsonl
  evidence.jsonl
  promotion.json

    Any path outside the two-file allowlist is a typed PolicyViolation. Protected controls are named in its evidence, and no successor SourceTree is created. Invalid UTF-8 values or malformed context-policy JSON are typed InvalidOutput. Empty or unchanged edits are typed ProposerFailure.

    The policy JSON must contain a positive integer max_documents and "order": "given". This validates the candidate before any held-out provider session is spent.

    Equal validation

    Baseline and candidate are evaluated on the same unseen row with:

    • the same pinned Claude model;
    • the same answer schema and normalized exact grader;
    • the same turn, timeout, and wall declarations;
    • the same public document order;
    • the same fixture-row checksum in evaluator identity.

    The harness artifact is the intended difference. A comparison result is one of:

    Result Meaning
    improvement Candidate exact score is higher.
    tie Both valid arms have the same exact score.
    regression Candidate exact score is lower.
    unrankable_typed_failure At least one arm produced no valid metric.

    The result also states automatic_promotion = False. Search or comparison may identify a better local artifact; neither the candidate nor this evaluator may deploy it.

    Minimal runnable mechanism

    from sealqa_labs import ClaudeSessionRunner
from sealqa_labs.meta_harness import run

result = run(ClaudeSessionRunner())

print("baseline:", result.artifacts["baseline"])
print("candidate:", result.artifacts.get("candidate"))
print("comparison:", result.artifacts.get("comparison"))
print("automatic promotion:", result.artifacts.get("automatic_promotion", False))
print("measurements:", result.measurements)
print("usage:", result.usage)
    Illustrative shape — live run, nothing captured
    baseline: <planner and context-policy SourceTree>
candidate: <allowlisted successor SourceTree or None>
comparison: <improvement, tie, regression, or unrankable typed failure>
automatic promotion: False
measurements: <equal-declaration validation measurements>
usage: <aggregated provider usage>

    Run it with:

    META_EVOLVE_LIVE_CLAUDE=1 uv run --extra claude \
  python examples/18_sealqa_research_labs/run_all.py meta_harness

    If mutation is invalid, only two sessions are needed: the diagnostic and mutator. The baseline/candidate validation pair is skipped because there is no admissible successor to compare.

    How to interpret a result

    An improvement means only that one diagnostic-informed mutation performed better on one unseen row. It does not establish that:

    • the planner change rather than the context-size change caused the gain;
    • the candidate generalizes to a broader repository task distribution;
    • the extra context is cost-effective;
    • the harness should be promoted;
    • the experiment can be durably replayed.

    A tie can still reveal that the mutation changed cost, document visibility, or failure behavior without changing exact accuracy. A regression is valuable evidence that the diagnostic adaptation overfit or removed useful context.

    Authority and validity checklist

    • Did the candidate change only the two permitted paths?
    • Was a forbidden-control proposal rejected without a successor?
    • Did the mutator see complete diagnostic evidence but no validation row?
    • Did both validation arms use identical declarations and document order?
    • Are failures reported by kind rather than converted to zero?
    • Is promotion still explicitly false?
    • Is this chapter still labeled a pre-M8 precursor?

    Change and predict

    Lower max_documents from 5 to 2 without changing the planner. Before running, predict:

    1. whether the useful document remains visible;
    2. whether cost or usage should change;
    3. whether the candidate will improve, tie, regress, or fail;
    4. why even an improvement would not authorize promotion.
