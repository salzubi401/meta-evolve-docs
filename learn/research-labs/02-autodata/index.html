    AutoData: improve a generation recipe with solver behavior

    Status: Experimental/live-only.

    Optional executable companion: open the canonical notebook. Everything needed to understand the lab is explained below.

    The concrete problem

    What is the current age of the oldest person to sail solo across the Pacific Ocean?

    This frozen row supplies the grounding documents from which a generator creates one new question-answer item. The artifact being improved is not the answer and not the generated row; it is the meta.Text generation recipe.

    The seed recipe says:

    Generate one unambiguous fact-seeking question answerable from the evidence.
Return its exact short answer and the document IDs used.

    The lab asks whether solver behavior can identify a useful generated item and provide evidence for rewriting that recipe.

    The idea

    AutoData-style generation uses downstream behavior as a quality signal:

    recipe ──► generated QA item
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
 restricted solver      informed solver
 question only          question + evidence
          └─────────┬─────────┘
                    ▼
       deterministic acceptance checks
                    │
                    ▼
              rewrite recipe

    The paper discusses weak and strong models. This lab deliberately uses the same pinned model with different context. The code roles are therefore named restricted_solver and informed_solver. Calling them weak and strong would hide the fact that context—not model capability—is the changed variable. That setup is a teaching simplification and a confounder.

    From Meta-Evolve principles to this algorithm

    The important move is to optimize the recipe, not to keep whichever single question looks nice. Each component has one authority:

    Role Concrete component What it contributes
    Mutable artifact meta.Text recipe A versioned instruction that can have a successor
    Generator Schema-constrained session Applies a recipe to public evidence and proposes one QA item
    Restricted probe Same model with question.md only Tests whether evidence is unnecessary or the answer leaks
    Informed probe Same model with selected evidence.md Tests whether cited evidence supports recovery
    Evaluator quality_checks() in local Python Converts observations into explicit acceptance reasons
    Proposer Recipe-rewriter session Turns the report into a generalized successor recipe
    Search shape Seed evaluation → one rewrite → successor evaluation Makes the causal comparison small and inspectable

    The generated QA item is an evaluation episode, not the durable thing being optimized. A seed recipe and successor recipe may each generate different questions; comparison asks whether the recipe produces an item that passes the same quality protocol.

    recipe artifact
  → generator applies it
  → two controlled solver contexts probe the item
  → deterministic evaluator produces accepted + reasons
  → rewriter uses that evidence to propose the next recipe artifact

    This is why the method is easy to build with Meta-Evolve: artifact lineage, bounded sessions, evidence, schema failure, and usage already exist. AutoData's domain logic is the small quality_checks() function and the choice of what the two solver arms may see.

    How _evaluate_recipe() assembles one evaluation

    The function first writes the public SealQA bundle to evidence.md and asks the generator for ITEM_SCHEMA. If generation fails validation, it returns one session plus a rejection report and spends no solver calls.

    For a valid item it builds two fresh workspaces:

    restricted_solver/
  question.md

informed_solver/
  question.md
  evidence.md   only documents named by evidence_doc_ids

    The code resolves local document IDs against the available public bundle. An unknown ID therefore cannot smuggle in external evidence; it becomes the deterministic unknown_evidence_document reason.

    Both _solver() calls use the same answer instructions, ANSWER_SCHEMA, SDK wrapper declaration, limits, and wall budget. Only the informed workspace has evidence. quality_checks() then reads the generator item and both SessionRecords. It never calls a model:

    schema valid?
IDs known?
answer text absent from question?
both solver sessions healthy?
restricted answer differs from reference?
informed answer exactly matches reference?

    The complete dictionary—generated item, solver outputs, accepted, and every reason—is written into LabResult.artifacts["evidence"]. The rewrite workspace contains the seed recipe and this report. The successor is lifted back into meta.Text and sent through the identical _evaluate_recipe() function.

    Walkthrough: one improvement cycle in three phases

    Each phase below is outer Python orchestration. Its generator, solver, and rewriter sessions are separate inner meta.run calls with one trial each; the lab does not run three greedy search iterations.

    Phase Meta-Evolve components What the candidate can observe Evaluator-owned result
    1. Evaluate seed recipe Seed meta.Text; generator request; restricted and informed solver requests Generator sees the public bundle; restricted solver sees only the generated question; informed solver sees only selected evidence quality_checks() records accepted/rejected reasons and a seed measurement
    2. Propose successor recipe Rewriter request; successor meta.Text Seed recipe, generated item, solver records, and the complete deterministic report Schema and non-identity checks decide whether a successor exists
    3. Evaluate and retain successor The same _evaluate_recipe() protocol; LabResult A fresh generator applies only the successor recipe; solver visibility remains split Successor acceptance measurement plus both recipes, reports, sessions, lineage, and usage

    The state transition is therefore:

    meta.Text(seed recipe)
  ── generator + two probes ──► seed acceptance report
  ── rewriter SessionRequest ──► meta.Text(successor recipe)
  ── same generator + two probes ──► successor acceptance report
  ── retain ──► LabResult

    The generated QA items are temporary evaluation episodes. They appear in the evidence record, but the lineage edge connects recipe to recipe. The local acceptance gate, not the generator or rewriter, decides whether each episode meets the declared behavior.

    The seven sessions

    One recipe evaluation uses three SDK sessions:

    1. generate a structured QA item from the frozen document bundle;
    2. ask the restricted solver with no documents;
    3. ask the informed solver with the generated item's selected documents.

    The complete path is:

    # Session Purpose
    1 Seed generator Apply the seed recipe.
    2 Seed restricted solver Test whether the question leaks or is already known.
    3 Seed informed solver Test whether selected evidence supports the reference answer.
    4 Recipe rewriter Generalize from the seed acceptance report.
    5 Successor generator Apply the rewritten recipe.
    6 Successor restricted solver Repeat the restricted check.
    7 Successor informed solver Repeat the grounded check.

    The local checks between sessions are deterministic and make no provider calls:

    3 seed sessions + 1 rewrite + 3 successor sessions = 7 maximum

    The generated-item contract

    The generator must return:

    {
  "question": "One generated fact-seeking question",
  "reference_answer": "One exact short answer",
  "evidence_doc_ids": ["doc-03", "doc-09"]
}

    The schema requires all three fields, non-empty strings, and no extra fields. Document IDs must exist in the candidate-visible bundle. They are stable local IDs—not upstream URLs or labels that reveal which source is gold.

    The reference_answer here belongs to the synthetic item produced by the generator. It is not the evaluator-only answer of the frozen SealQA row.

    Deterministic quality checks

    An item is accepted only when every check passes:

    Check Rejection reason Meaning
    Schema structured-output failure Required fields are missing or malformed.
    Evidence IDs unknown_evidence_document The recipe cited a document it never received.
    Leakage reference_answer_leaked_in_question The question gives away its own answer.
    Restricted exact answer restricted_solver_already_knows_answer The item may be trivial, memorized, or leaking.
    Informed exact answer informed_solver_cannot_recover_answer Selected evidence does not establish the answer.
    Session health solver_failure At least one solver produced no rankable answer.

    In compact form, the desired behavior is:

    restricted answer != reference answer
informed answer    == reference answer

    This is a proxy for grounded usefulness, not proof. The restricted model may guess incorrectly despite already knowing the fact, and the informed model may match for the wrong reason.

    Recipe rewriting and lineage

    The rewriter sees:

    • the seed recipe;
    • the complete generated item;
    • both solver answers or failures;
    • the acceptance decision and rejection reasons.

    It is told to generalize rather than copy the generated question or answer. Its structured output is simply:

    {"recipe": "The complete successor generation recipe."}

    The result retains both recipes, both generated examples, both solver pairs, both acceptance reports, evaluator identity, typed failures, and aggregate usage. That makes the causal story inspectable:

    seed recipe + seed rejection evidence ──► successor recipe

    Minimal runnable mechanism

    from sealqa_labs import UserSdkSessionRunner
from sealqa_labs.autodata import run

result = run(UserSdkSessionRunner(agent_factory=build_agent))

print("seed recipe:", result.artifacts["seed_recipe"])
print("successor recipe:", result.artifacts.get("successor_recipe"))
print("evidence:", result.artifacts["evidence"])
print("measurements:", result.measurements)
print("usage:", result.usage)
    Illustrative shape — live run, nothing captured
    seed recipe: <original generation instructions>
successor recipe: <evidence-guided rewritten instructions>
evidence: <generated items, solver answers, decisions, and rejection reasons>
measurements: <seed and successor acceptance metrics or typed failures>
usage: <aggregated provider usage>

    Run it with:

    META_EVOLVE_LIVE_SDK=1 uv run python your_sealqa_driver.py autodata

    How to read the result

    Compare the two acceptance reports rather than looking only at the final flag:

    Seed Successor Interpretation
    rejected accepted The rewrite fixed the observed gate on this one attempt.
    rejected rejected Inspect whether the reason changed; the rewrite may still have altered behavior.
    accepted accepted There may have been no useful error signal for rewriting.
    accepted rejected The rewrite regressed the recipe.
    failure any The failed arm is unrankable and should not be treated as rejection.

    One generated item per recipe is a mechanism demonstration. It does not estimate a stable acceptance rate, diversity, or downstream training value.

    Leakage and comparison checklist

    • The restricted workspace contains only question.md.
    • The informed workspace adds evidence.md; model and bounds stay identical.
    • Neither solver receives the frozen row's hidden answer or URLs.
    • The generator may see public document text but no gold label.
    • The rewriter sees generated evidence, not the held-out behavior of future generated items.
    • Same-model/different-context results are not described as weak-vs-strong model evidence.

    Change and predict

    Modify the recipe to require two independent evidence document IDs. Predict:

    1. whether unknown-document rejection becomes more common;
    2. whether the informed solver becomes more reliable;
    3. whether leakage changes at all;
    4. what a rejected successor would teach you about the recipe rather than the model.
