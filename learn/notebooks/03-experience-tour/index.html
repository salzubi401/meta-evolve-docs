    Reuse experience without losing causality

    Status: Shipped.

    An improvement loop becomes more useful when a later proposal can learn from earlier failures. It becomes much harder to trust if “memory” is an invisible global variable. This chapter shows how Meta-Evolve exposes prior work as bounded, time-scoped, audited experience.

    Open the canonical executed notebook only to run the cells. The entire mechanism and result are explained here.

    What it teaches

    Meta-Evolve splits experience reuse into four ideas:

    Graph       what committed records existed at a logical time
Push        what a policy selected before a proposal began
Pull        what the proposer chose to inspect during its work
Derivation  which observed records the proposal says it actually used

    Evaluation remains independent. Reading a previous failure may influence a proposal, but it cannot change the grader, grant more budget, or turn a failed evaluation into a success.

    The running problem

    The seed is 0. Ordinary proposals add one. Candidates 1, 2, and 3 are known traps: the evaluator returns a typed EvaluatorFailure, not a score. After observing two distinct failures, the proposer can jump to 10.

    def evaluate(candidate):
    if candidate in {1, 2, 3}:
        return EvaluatorFailure(message=f"known trap at {candidate}")
    return candidate

def propose(parent, context):
    failures = observed_failures(context)
    candidate = 10 if len(failures) >= 2 else parent + 1
    return ProposalResult(candidate=candidate, derived_from=used_refs)

    The budget is always four evaluations and three successor trials. A custom chain search makes each successful candidate the next parent so the experiment isolates experience access rather than parent-selection behavior.

    Four controlled variants

    The task, seed, proposer, evaluator, search, root seed, and budget are fixed. Only experience declarations change:

    Variant Pushed context Pull capability
    no-memory No No
    push-only Failed ancestors No
    pull-only No Bounded reader
    combined Failed ancestors Bounded reader

    This is a valid A/B-style design because memory strategy is the declared independent variable. Run.compare() reports whether context and pull declarations match instead of pretending the arms are identical.

    All arms spend evaluations=4, trials=3. Only memory-aware variants can observe both earlier traps and produce 10. The final no-memory proposal tries 3 and fails.

    This demonstrates the mechanism on a constructed task. It does not prove memory generally helps; experience can also distract a proposer, suppress novelty, or consume model context.

    The temporal experience graph

    The graph is a read model over committed occurrences:

    step 0: seed proposal → artifact 0 → evaluation score 0
step 1: decision → proposal 1 → artifact 1 → evaluator failure
step 2: decision → proposal 2 → artifact 2 → evaluator failure
step 3: decision → proposal 10 → artifact 10 → evaluation score 10

    Occurrences matter. Two trials that produce byte-identical artifacts remain different causal events because they may have different parents, observations, usage, and failures.

    An ExperienceQuery(as_of=2) may see committed records through logical step 2; it cannot see step 3. This prevents future leakage during replay and live proposal.

    historical = graph.state_at(ExperienceQuery(
    task_id=graph.task_id,
    run_id=combined.id,
    as_of=2,
))
print("visible steps as_of=2:", [node.logical_step for node in historical.nodes])
print("frontier steps:", [node.logical_step for node in state.nodes])
    Output
    visible steps as_of=2: [0, 1, 2]

    Push: policy-selected context

    A context policy runs before the proposer. The example's FailedAncestors policy walks the current parent lineage and selects only failed evaluations:

    projection = combined._projection()
for selected in projection.context_selections:
    refs = tuple(record.ref.kind for record in selected.bundle.records)
    print(
        f"step={selected.bundle.records[-1].logical_step if refs else '-'}",
        f"reason={selected.bundle.reason!r}",
        f"refs={refs}",
        f"usage={selected.bundle.usage}",
    )
print("M3.2 declaration:", projection.context_declaration.spec)
    Output
    step=- reason='failed ancestor evaluations' refs=() usage=ContextUsage(records=0, chars=0)
step=1 reason='failed ancestor evaluations' refs=('evaluation',) usage=ContextUsage(records=1, chars=1098)
step=2 reason='failed ancestor evaluations' refs=('evaluation', 'evaluation') usage=ContextUsage(records=2, chars=2197)
M3.2 declaration: ContextSpec(policy=PolicyRef(name='failed-ancestors', version='1', origin='local'), max_records=20, max_chars=8000)

    The committed ContextBundle contains:

    • exact structured records and references;
    • a canonical rendered form for a text consumer;
    • the selection reason;
    • truncation status;
    • record and character usage.

    It is a snapshot, not a live database handle. Replay checks the recorded bundle instead of calling the selector again.

    Pull: proposer-directed inspection

    PullAccess grants a trial-limited reader. The proposer can search, open, traverse, or compare prior records within declared caps:

    meta.PullAccess(
    max_operations=20,
    max_results=20,
    max_records=100,
    max_chars=32_000,
)

    Every operation is recorded as an attempt followed by success, opaque denial, or exhaustion. On the final trial, the example searches two failed evaluations, opens both, and compares their trial occurrences.

    The grant's as_of boundary is fixed before proposal execution. A tool call cannot move it forward and inspect the trial currently being produced.

    Observation is not use

    A proposer may receive ten records and rely on only two. derived_from names the ordered references it claims caused the proposal:

    return ProposalResult(
    candidate=10,
    derived_from=(failure_one_ref, failure_two_ref),
)

    The coordinator validates that each reference was actually visible through the committed push-then-pull observation ledger. Invented, future, duplicate, or out-of-order references become a typed policy failure; no candidate is committed.

    Memory usage is separate from task usage

    The result output above reports task and memory usage independently. Experience reads do not consume evaluation/trial budget, but they are still measured. A production experiment must also count how retrieved characters affect provider tokens and cost.

    Authority map

    Component May do May not do
    Context policy Select prior records under caps See future records or mutate history
    Pull grant Authorize bounded read operations Expand its own limits
    Proposer Observe granted records and propose Change evaluator or award a score
    Coordinator Validate visibility, usage, derivation Invent proposal intent
    Evaluator Return metric or typed failure Rewrite the candidate

    What to notice

    • The first successor has no prior failure to reuse.
    • Typed failures can be valuable evidence without becoming low scores.
    • Push is chosen by policy; pull is chosen by the proposer under a grant.
    • Both channels are bounded and recorded at a logical time.
    • derived_from records claimed use, not everything that was visible.
    • Experience improves this toy result without changing task budget.

    Interpretation questions

    1. Why can the first proposal not cite an evaluator failure?
    2. Why is a failed evaluation useful but unrankable?
    3. What prevents a pull-enabled proposer from reading its future result?
    4. Why record derivation separately from the context bundle?
    Answers 1. Only the seed evaluation exists before the first proposal, and it succeeds. 2. It contains diagnostic information, but no valid metric exists for search ranking. 3. The grant has a committed strictly-prior `as_of` boundary. 4. Visibility does not prove causal use; derivation records the proposer's narrower explicit claim.

    Change and predict

    Change the task so only one observed failure is required before jumping to 10.

    Predict: each memory-aware variant should succeed one trial earlier; the no-memory arm still cannot. The task budget ceiling stays four evaluations, but actual usage may shrink if the objective has a satisfaction threshold.
