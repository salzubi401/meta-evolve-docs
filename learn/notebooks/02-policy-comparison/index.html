    Compare search policies fairly

    Status: Shipped.

    The previous chapter explained how policies behave on one run. This chapter shows how to compare them without accidentally changing the task, budget, or measurement at the same time.

    Open the canonical executed notebook if you want the cells. The benchmark, output, and interpretation are complete below.

    What it teaches

    A policy comparison is valid only when the things that define performance are held fixed. In this benchmark, all three policies share:

    • target 12 and score -abs(candidate - 12);
    • seed artifact 0;
    • proposer moves (-2, 1, 5);
    • nine evaluations and eight successor trials;
    • root seeds 0 through 39;
    • objective direction and satisfaction threshold.

    Only the search policy and its own configuration differ.

    Why one run is not enough

    The proposer samples a move from a recorded random stream. One root seed can favor one policy by chance. A sweep repeats the same declared comparison over 40 root seeds and aggregates outcomes:

    for root_seed in range(40):
    runs = [
        meta.run(
            task=TASK,
            seed=0,
            proposer=propose,
            search=make_policy(),
            random_seed=root_seed,
        )
        for make_policy in POLICY_FACTORIES
    ]

    This is still a small deterministic illustration, not a claim about all search problems. Multiple seeds reveal variability inside this benchmark; they do not create task diversity.

    What must stay equal

    Use this table when designing a comparison:

    Declaration Why changing it confounds the result
    Task/evaluator Changes what “good” means
    Objective order Changes ranking and stopping
    Artifact kind Changes valid candidate representation
    Seed artifact Changes the starting difficulty
    Proposer identity Changes which candidates can be produced
    Effective budget Lets one arm buy more attempts or time
    Evaluation environment Changes the conditions being measured

    Policy choice, policy configuration, and root random seed may differ because they are the independent variables this benchmark is studying.

    Run.compare() checks these declarations before returning a comparison. It does not infer equality from similar output or function names.

    The observed distributions

    The committed benchmark reports:

    Policy Solved Best-score behavior Why
    BestOfN 0/40 Always -7 Only one-step values -2, 1, 5 are reachable
    Greedy 15/40 Scores range -9 to 0 Improvements accumulate along one chain
    Population 14/40 Scores range -10 to 0 Several branches compete for a three-member archive

    “Solved” means the best score equals 0, not merely that the run completed. BestOfN's invariant -7 is not bad luck: it is a proof from its topology and the move set. Its best reachable candidate is always 5.

    Greedy and Population sometimes stop early after reaching the satisfaction threshold. Their evaluation-count distributions therefore include values below nine. BestOfN never solves and always consumes nine evaluations.

    Read a distribution, not just a mean

    Ask the report object for the exact solve count and score distribution:

    greedy = next(report for report in reports if report.policy == "Greedy")
print(f"Greedy solved: {greedy.solve_count}/{greedy.run_count}")
print("Greedy scores:", dict(greedy.score_distribution))
    Output
    Greedy solved: 15/40
Greedy scores: {-9: 1, -8: 1, -5: 3, -4: 2, -3: 3, -2: 3, -1: 12, 0: 15}

    That tells more than an average:

    • 15 runs solved exactly;
    • 12 finished one unit away;
    • a small tail performed much worse;
    • success is not guaranteed by the policy.

    Population solves almost as often but has a different tail. If one application cares about worst-case quality, solve rate alone is insufficient. A serious study would predeclare the summary statistics and uncertainty treatment rather than selecting whichever view looks best afterward.

    Lineage explains the mechanism

    The report prints one representative winning lineage per policy:

    topologies = {
    "BestOfN": "star spoke",
    "Greedy": "chain",
    "Population": "winning tree branch",
}
for report in reports:
    print(
        f"{report.policy}: {topologies[report.policy]} "
        f"{list(report.representative_lineage)} "
        f"(seed {report.representative_seed})"
    )
    Output
    BestOfN: star spoke [0, 5] (seed 0)
Greedy: chain [0, 5, 10, 11, 12] (seed 1)
Population: winning tree branch [0, 5, 10, 11, 12] (seed 0)

    Identical winning values do not imply identical search. Population may have spent trials maintaining sibling branches that are absent from this one path. Use result.trials() for all attempts and result.lineage() for causal ancestry of one artifact.

    How Run.compare() protects the claim

    for other_name in ("BestOfN", "Population"):
    comparison = runs["Greedy"].compare(runs[other_name])
    winner = comparison.winner.policy.name if comparison.winner else "tie"
    print(
        f"Greedy vs {other_name}: winner={winner}, "
        f"same_random_seed={comparison.same_random_seed}",
    )
    Output
    Greedy vs BestOfN: winner=greedy, same_random_seed=True
Greedy vs Population: winner=greedy, same_random_seed=True

    The comparison first verifies compatibility. If evaluator, proposer, objective, budget, artifact kind, or initial artifact differs, it raises rather than presenting a misleading winner.

    Exact primary-score equality is a tie. Lower token use or fewer evaluations does not silently break a score tie because that would introduce an undeclared secondary objective. Declare cost as an objective or constraint if it should affect ranking.

    Identity is a declaration, not omniscience

    Local callable identity uses a declaration based on module and qualified name. Two callables with matching names are not mathematically proven equivalent. Configured adapters should hash behavior-affecting fields into their component version, and durable registered components should declare configuration.

    For example, changing a model ID, timeout, hidden case suite, or grader threshold while preserving the same component identity makes a comparison look controlled when it is not. Identity must cover everything that can change behavior but is not already represented by task and run declarations.

    Claims this benchmark supports

    It supports:

    • the three shipped policies produce different topology and distributions on this exact number-search task;
    • BestOfN cannot compose moves and therefore cannot solve this task;
    • Greedy and Population sometimes solve under the equal declared budget;
    • committed summaries and lineages reproduce the recorded outcomes.

    It does not support:

    • Greedy is generally superior to population search;
    • 40 deterministic root seeds provide broad statistical evidence;
    • the result transfers to language models, source code, or noisy evaluators;
    • local callable names prove behavioral equivalence across code changes.

    What to notice

    • Fairness is a property of declarations and evaluation conditions, not equal row counts in a report.
    • A root-seed sweep studies stochastic variation, not task generalization.
    • Early satisfaction changes actual usage while the maximum budget stays equal.
    • Lineage gives a mechanistic explanation for observed score distributions.
    • A comparison reports ties honestly and never uses usage as a hidden tiebreaker.

    Interpretation questions

    1. Why is BestOfN's 0/40 result deterministic despite random moves?
    2. Why may Greedy use fewer evaluations than BestOfN under an equal budget?
    3. Can we conclude Population is worse because it solved one fewer seed?
    4. Why is changing a timeout a comparison change even if no timeout occurs?
    Answers 1. Every independent proposal is one move from zero, and the best reachable value is always `5`. 2. Greedy sometimes reaches the declared satisfaction threshold and stops; equal budgets are ceilings, not mandatory spending. 3. No. This benchmark is small, task-specific, and does not quantify whether the one-run difference is stable or meaningful elsewhere. 4. Timeout changes the authorized execution regime and could affect which results are observable; identity and compatibility must describe potential behavior, not only what happened once.

    Change and predict

    Add 12 to MOVES.

    Before running:

    • BestOfN can now solve whenever at least one of eight independent samples chooses 12; its formerly fixed -7 distribution must change.
    • Greedy and Population can also solve in one step, but they already had multi-step paths to the target, so the mechanism changes less radically.
    • The proposer identity or version must change because its behavior changed.

    Run the sweep in a temporary copy. Do not compare the changed run to the original as though only policy differed—the proposer declaration is now a new experimental condition.
