    Recover a durable run after a crash

    Status: Shipped.

    A useful long-running experiment must survive process death without repeating committed work or inventing a different history. This chapter explains how durable-local storage, replay, registered components, and meta.resume compose to provide that guarantee.

    Use the executed notebook to rerun the fault matrix; this page contains the full explanation.

    What it teaches

    Crash recovery is not “start a similar run again.” It is:

    reopen one exact run id
  → validate its committed event prefix
  → reconstruct the last complete logical state
  → rebuild verified components
  → continue only the missing authorized work
  → reach the same final event stream as uninterrupted execution

    The guarantee depends on deterministic, retry-safe components and atomic commits. A live, non-reconstructable callback cannot honestly provide it.

    The running problem

    The example climbs from 0 to target 6 by proposing parent + 1:

    def propose(parent, context):
    return parent + 1

def evaluate(candidate):
    return -abs(candidate - 6)

    Reaching 6 requires six successor trials and seven evaluations including the seed. The task permits eight evaluations and Greedy permits eight successor trials, leaving slack so the run stops because it satisfies the objective rather than because budget expires.

    Why ordinary local callables are insufficient

    An in-memory function object cannot be reconstructed after the Python process dies. Durable mode therefore requires registered module-level components:

    registry = meta.Registry()
proposer_ref = registry.register_proposer(
    "example:propose", "1", propose,
    deterministic=True,
    retry_safe=True,
)
evaluator_ref = registry.register_evaluator(
    "example:evaluate", "1", evaluate,
    deterministic=True,
    retry_safe=True,
    configuration={"target": 6},
)

    The durable event stream records typed component references and manifests. On resume, the supplied registry must resolve compatible implementations whose source and configuration match those manifests.

    The target belongs in evaluator configuration because changing it changes behavior even if the Python function name remains the same.

    Starting a durable run

    run = meta.run(
    task=build_task(evaluator_ref),
    seed=0,
    proposer=proposer_ref,
    search=meta.Greedy(max_trials=8),
    storage=meta.Storage.durable(path),
    mode="durable-local",
    registry=registry,
)

    Run identity derives from the declarations, not from the storage directory. Starting the same task, seed, component references, policy, and budgets on two paths produces the same run ID.

    Atomic batch commits

    The coordinator groups each state transition into an all-or-none storage commit. A simplified run looks like:

    batch 1  run + seed records
batch 2  search decision
batch 3  proposal/trial outcome
batch 4  evaluation
batch 5  next decision
...

    If power fails between batches, every earlier batch is durable and the next is absent. If it fails while a batch is being written, the storage transaction commits all of it or none of it. Recovery never has to interpret half an evaluation.

    The notebook's CrashAfter wrapper is only a deterministic test instrument. It permits the first n real commits and raises before the next. Production users do not install it or touch the internal commit strategy; real operating system or hardware failure supplies the interruption.

    The three recovery frontiers

    Replay classifies the committed prefix:

    Frontier Last durable fact What resume does next
    DECISION_READY Previous work complete Ask search for the next decision
    TRIAL_DECIDED Trial authorization committed Run the authorized proposer work
    EVALUATION_PENDING Candidate outcome committed Evaluate that committed artifact

    These states prevent duplicate work. For example, a committed candidate with no evaluation is evaluated; the proposer is not called again to create a possibly different candidate.

    Pull experience operations add a related boundary: an attempted but unresolved read is rolled forward using the same committed operation ID.

    The sweep classifies every interior boundary:

    phases = {}
total_a = boundaries + 1
for k in range(1, total_a):
    p = adir / f'phase{k}'
    s = meta.Storage.durable(p)  # install + run on one handle (see sweep note)
    install_crash(s, n=k)
    try:
        main.start_run(s, main.build_components())
    except CRASH:
        pass
    events = meta.Storage.durable(p).events.read(rid_a)
    phase = classify_frontier(events, replay_run_projection(rid_a, events)).name
    phases.setdefault(phase, []).append(k)
for name, ks in phases.items():
    print(f'  {name:<18} at boundaries {ks}')
    Output

    The demonstrated lifecycle

    The uninterrupted reference reaches best 6 in 49 events over 23 committed batches. Then the notebook interrupts the same logical run shape:

    Reopen is not resume

    These operations answer different questions:

    cold = meta.Run(rid_a, meta.Storage.durable(adir / 'ref'))
print('best() from a cold store :', cold.best().value)
print('winning lineage steps    :', [t.logical_step for t in cold.lineage()])
    Output
    best() from a cold store : 6
winning lineage steps    : [0, 1, 2, 3, 4, 5, 6]

    Run(...) rebuilds a read-only result from committed facts. It performs no new work and can inspect a completed or partial history where queries are defined.

    continued = meta.resume(
    run_id,
    storage=reopened_storage,
    registry=registry,
)

    resume may invoke search, proposer, and evaluator to finish missing work. It therefore requires reconstruction authority and verified components.

    Resuming an already completed run is a no-op. Concurrent resume attempts use optimistic append control: one commits, while a stale writer receives EventStreamConflict rather than duplicating a transition.

    What cannot resume

    A run may retain durable history without being resumable. Local patch callbacks, command evaluator objects, provider sessions, or closures can be inspectable after reopening while lacking a portable reconstruction contract.

    Meta-Evolve raises CapabilityError instead of silently substituting a different component. Durable storage is evidence retention; resumability is an additional capability.

    What to notice

    • The event log is append-only; crash simulation never truncates it.
    • Atomicity prevents partial logical batches.
    • Replay determines exactly which work is missing.
    • Component manifests protect behavior across process restart.
    • Run identity is logical and independent of the storage path.
    • Resume does not mean arbitrary live-model output becomes reproducible.

    Interpretation questions

    1. Why does a committed candidate with no evaluation not run its proposer again?
    2. Why must the evaluator's target be in its manifest configuration?
    3. What is the difference between reopening and resuming?
    4. Can a non-deterministic remote provider promise a byte-identical resumed result merely because events are durable?
    Answers 1. The proposal result already exists; rerunning could create a second outcome for one authorized trial. Resume continues at `EVALUATION_PENDING`. 2. The target changes scoring behavior while the function's name and source may stay constant. 3. Reopen reads committed history; resume is authorized to reconstruct components and continue missing work. 4. No. Durable observations can be retained, but equivalent future provider output requires stronger provider-specific guarantees.

    Change and predict

    Move the simulated crash from batch 11 to batch 12.

    Predict which frontier the new prefix reaches, whether the event count grows, and which operation resume performs first. The final best and complete event stream must remain identical to the reference.
