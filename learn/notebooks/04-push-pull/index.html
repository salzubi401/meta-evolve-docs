    Inspect pushed context and pulled experience

    Status: Shipped.

    The previous chapter introduced two routes to prior work. This chapter follows the exact records so you can decide which route belongs in a real agent setup.

    Open the canonical executed notebook only if you want to manipulate the saved experiment.

    What it teaches

    Push and pull answer different questions:

    Push: “What should every proposer receive before it starts?”
Pull: “What should this proposer be allowed to investigate while working?”

    They can expose the same underlying evaluation, but the decision maker, timing, audit record, and cost are different.

    Start from one trial

    Before a successor proposal runs, the coordinator prepares two independent inputs:

    projected history
   │
   ├─ context policy.select(...) ──► immutable ContextBundle
   │
   └─ experience declaration ──────► trial-scoped ExperienceGrant
                                          │
proposal starts                           └─ search/open/compare tools

    Both are limited to prior committed logical time. Neither provides evaluator, budget, storage-write, or promotion authority.

    Pushed context step by step

    The FailedAncestors policy selects failed evaluations from the current parent's ancestry. Its output over three proposals is:

    push_run = results["push-only"][0]
push_projection = push_run._projection()

for index, selected in enumerate(push_projection.context_selections, start=1):
    records = selected.bundle.records
    labels = tuple(
        f"{record.ref.kind}@{record.logical_step}" for record in records
    )
    print(
        f"trial={index}",
        f"selected={labels}",
        f"chars={selected.bundle.usage.chars}",
    )
    Output
    trial=1 selected=() chars=0
trial=2 selected=('evaluation@1',) chars=1098
trial=3 selected=('evaluation@1', 'evaluation@2') chars=2197

    Why the sequence grows:

    1. Before trial 1, no successor has failed.
    2. Trial 1 evaluates candidate 1 and fails.
    3. Before trial 2, that one failure is an ancestor observation.
    4. Trial 2 evaluates candidate 2 and fails.
    5. Before trial 3, both failures are available.

    The final selection exposes the exact bundle metadata:

    bundle = push_projection.context_selections[-1].bundle
print("reason:", bundle.reason)
print("truncated:", bundle.truncated)
print("usage:", bundle.usage)
print("refs:", tuple(
    f"{record.ref.kind}@{record.logical_step}" for record in bundle.records
))
    Output
    reason: failed ancestor evaluations
truncated: False
usage: ContextUsage(records=2, chars=2197)
refs: ('evaluation@1', 'evaluation@2')

    Structured proposers can inspect records; a model adapter can use the bounded rendered form. Recording both prevents the rendered prompt from becoming the only evidence of what was supplied.

    Why a bundle is a snapshot

    Once selected, a bundle cannot observe newly committed work. The proposal gets stable input, replay can validate exact references and bytes, and concurrent workers cannot silently see different “latest” histories. Replay reads the snapshot rather than rerunning FailedAncestors under changed code or data.

    Pull grants step by step

    Each successor receives a fresh grant whose as_of equals the last committed logical step:

    pull_run = results["pull-only"][0]
pull_projection = pull_run._projection()

for issued in pull_projection.experience_grants:
    operations = pull_projection.operations_for(issued.grant.trial_id)
    print(f"grant as_of={issued.grant.as_of}")
    for attempt, resolution in operations:
        result = getattr(resolution, "result", None)
        count = len(result.references) if result is not None else 0
        print(
            f"  {attempt.request.operation:<7}",
            f"{type(resolution).__name__:<28}",
            f"refs={count}",
        )
    Output
    grant as_of=0
  search  ExperienceOperationSucceeded refs=0
grant as_of=1
  search  ExperienceOperationSucceeded refs=1
  open    ExperienceOperationSucceeded refs=1
grant as_of=2
  search  ExperienceOperationSucceeded refs=2
  open    ExperienceOperationSucceeded refs=1
  open    ExperienceOperationSucceeded refs=1
  compare ExperienceOperationSucceeded refs=2

    An operation has two durable phases:

    ExperienceOperationAttempted
          │
          ├─► ExperienceOperationSucceeded(result references + bounded data)
          ├─► ExperienceOperationDenied(opaque reason)
          └─► ExperienceOperationExhausted(which cap was reached)

    Recording the attempt separately matters for crash recovery: if a process dies after the attempt commits but before resolution, resume can recognize and roll forward that incomplete operation.

    The four useful pull operations

    Search returns bounded matching references; open resolves an authorized reference; traverse follows causal relationships; and compare returns structured views of named occurrences. All remain inside the temporal grant and consume operation, result, record, and character caps.

    The canonical observation ledger

    Derivation validation needs one deterministic order across both channels. The ledger is built as:

    1. pushed bundle references, in bundle order
2. successful pull result references, in operation order
3. structured references contained in those results
4. duplicates removed at their first occurrence

    For the combined arm's final proposal, inspect the ledger and declaration together:

    combined_run = results["combined"][0]
combined = combined_run._projection()
final = combined.completed_trials[-1].trial.id
proposal = combined.proposal_for(final)
ledger = observation_ledger(combined, final)

print("ledger kinds:", tuple(reference.kind for reference in ledger))
print("declared kinds:", tuple(ref.kind for ref in proposal.derived_from))
positions = tuple(ledger.index(ref) for ref in proposal.derived_from)
print("declared positions:", positions)
print("ordered subsequence:", positions == tuple(sorted(positions)))
    Output
    ledger kinds: ('evaluation', 'evaluation', 'trial', 'trial', 'decision', 'decision', 'decision_explanation', 'decision_explanation', 'proposal', 'proposal', 'artifact', 'artifact', 'outcome', 'outcome')
declared kinds: ('evaluation', 'evaluation', 'trial', 'trial')
declared positions: (0, 1, 2, 3)
ordered subsequence: True

    Those positions are (0, 1, 2, 3), a valid ordered subsequence. The proposer may omit observed records it did not use, but it may not reorder or invent them.

    Choosing push, pull, or both

    Choose When it fits
    Push Every proposal needs a stable compact briefing and predictable size
    Pull Relevant history depends on what the proposer discovers
    Both A required briefing should coexist with selective investigation

    Combined access may expose the same fact twice, so measure duplicated content.

    Usage accounting

    The public result API reports the committed totals:

    for name, (result, _) in results.items():
    usage = result.experience_usage()
    print(
        f"{name:<10}",
        f"context=({usage.context.records}, {usage.context.chars})",
        f"pull=({usage.pull.operations}, {usage.pull.results},",
        f"{usage.pull.records}, {usage.pull.chars})",
    )
    Output
    no-memory  context=(0, 0) pull=(0, 0, 0, 0)
push-only  context=(3, 3295) pull=(0, 0, 0, 0)
pull-only  context=(0, 0) pull=(7, 8, 20, 20559)
combined   context=(3, 3295) pull=(7, 8, 20, 20855)

    Counts are cumulative over the run. results counts returned result objects; records counts structured records contained in them. They need not match.

    Memory usage is not evaluation/trial usage. For a live model, however, rendered characters often become provider tokens, so the evaluator or proposer should also report actual token and wall usage.

    Failure and denial semantics

    Exhaustion and denial are not empty search results:

    • empty success means the query was authorized and matched nothing;
    • denial means policy refused the operation without leaking protected detail;
    • exhaustion means an explicit grant cap was reached;
    • infrastructure failure means the reader could not reliably answer.

    Adapters must preserve these differences. A silent fallback from pull to “no memory” changes the experiment and hides a failure.

    What to notice

    • Push records the experimenter's selection; pull records the agent's choices.
    • Grants are trial-scoped and strictly prior.
    • A search reference and an opened record are separately auditable.
    • The ledger is push-then-pull and deduplicated deterministically.
    • Memory access has its own cumulative accounting.
    • Neither channel can modify the durable graph.

    Interpretation questions

    1. Why not give the proposer a mutable graph object directly?
    2. What does an empty successful search prove?
    3. Why are push records ordered before pull results in the ledger?
    4. When is pull worth its larger usage footprint?
    Answers 1. It would create ambient, time-varying authority and make replay impossible to validate exactly. 2. The operation was authorized and no visible prior record matched; it does not mean the reader failed. 3. Push is observed before proposal execution; pull observations occur later in committed operation order. 4. When selective investigation can find relevant evidence that a stable small pushed bundle cannot anticipate, and the added cost is measured.

    Change and predict

    Set PullAccess.max_operations=3.

    The final proposer needs four operations—search, open, open, compare. Predict that the fourth attempt exhausts the grant, pull usage stops at the cap, and a proposal that requires the comparison reference cannot validly cite it. The coordinator must record exhaustion rather than silently omit the operation.
