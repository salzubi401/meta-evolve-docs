    Start here: one improvement loop

    Status: Shipped.

    Meta-Evolve repeatedly creates a candidate, evaluates it, and decides whether that candidate should influence the next attempt. Begin with a three-item checklist so every value has an obvious meaning and no randomness gets in the way.

    From the repository root, run:

    uv run python examples/00_checklist/main.py
    Output
    ['outline', 'draft', 'review']
[[], ['outline'], ['outline', 'draft'], ['outline', 'draft', 'review']]

    Run uv sync --locked once before the command if this checkout has not been installed yet.

    The first line is the best artifact: the three completed checklist items. The second line is its lineage: the exact chain of checklist states that led there.

    The problem in everyday language

    Imagine a checklist with three items:

    start:       []
attempt 1:   ['outline']
attempt 2:   ['outline', 'draft']
attempt 3:   ['outline', 'draft', 'review'] — success

    The immutable artifact contains the actual completed items. Lists make the printed output familiar; the program stores each state as an immutable tuple.

    The complete program

    from meta_evolve import Budget, Greedy, Maximize, Task, run


ITEMS = ("outline", "draft", "review")


def complete_one(completed, _context):
    return (*completed, ITEMS[len(completed)])


def count_completed(completed):
    return sum(item in completed for item in ITEMS)


task = Task(
    evaluator=count_completed,
    objectives=(Maximize("completed", satisfy=len(ITEMS)),),
    budget=Budget(evaluations=4, trials=3),
)
result = run(
    task=task,
    seed=(),
    proposer=complete_one,
    search=Greedy(max_trials=3),
)


def main():
    print(list(result.best().value))
    print([list(trial.artifact.value) for trial in result.lineage()])


if __name__ == "__main__":
    main()

    Read it as five declarations:

    Declaration Value here Responsibility
    Task Complete outline, draft, and review Defines evaluation, success, and limits
    Seed () The empty checklist
    Proposer Append the next named item Creates a candidate from the chosen parent
    Evaluator Count recognized completed items Measures the candidate independently
    Search Greedy Chooses what to build on and when to stop

    Those components are separate because changing how candidates are generated should not silently change what counts as success.

    Follow one attempt

    The empty seed is evaluated first and scores 0. Then one successor attempt is:

    Greedy chooses parent ()
  → complete_one(()) proposes ('outline',)
  → count_completed(('outline',)) returns score 1
  → Greedy sees an improvement and retains ('outline',)

    The same cycle appends draft, then review. The objective declares three recognized items satisfactory, so the run stops.

    The proposer creates a value; it does not give that value a score. The evaluator scores it; it does not choose the next parent. The coordinator keeps these roles and their records separate.

    Read the result object

    The run returns more than the final value. These are the public inspection methods used throughout the learning path:

    """Read the completed checklist through the public result API."""

from main import result


summary = result.summary()
print("best:", list(result.best().value))
print("primary score:", summary.primary_score)
print("task usage:", summary.usage)
print("winning lineage:", [list(value) for value in summary.winning_lineage])
    Output
    best: ['outline', 'draft', 'review']
primary score: 3
task usage: Usage(evaluations=4, trials=3, tokens=0, wall_seconds=0.0)
winning lineage: [[], ['outline'], ['outline', 'draft'], ['outline', 'draft', 'review']]

    best() decodes the winning artifact. summary() exposes the selected score, resource use, and winning lineage without requiring internal event or storage objects. Later chapters use trials() for every attempted outcome and compare() for compatible runs.

    Understand the budget

    Budget(evaluations=4, trials=3)
    • The seed consumes one evaluation.
    • Each of three successor attempts consumes one trial and, when valid, one evaluation.
    • Therefore this complete path needs four evaluations and three trials.

    Greedy(max_trials=3) is the policy's stopping limit. Budget(...) is the coordinator-enforced resource ceiling. Neither the proposer nor its candidate can increase either one.

    Understand Greedy

    Greedy keeps a single current best artifact, called the incumbent:

    candidate is better? ── yes ──► use it as a future parent
          │
          no
          ▼
record the result, but keep the previous parent

    Every checklist proposal adds a recognized item and improves the score, so the winning lineage contains every step. Later examples include rejected attempts; those remain recorded evidence but do not become ancestors of the winner.

    Why the separation matters

    Suppose an unreliable proposer claims that 100 items are complete. It still cannot award itself success. In a real task, an evaluator would inspect the actual artifact and return independent evidence. Evaluation, budgets, stored history, and external promotion remain outside candidate authority.

    Task ── owns evaluator, objective, and budget
 │
seed ── evaluated first ──► Search chooses a parent
                              │
                              ▼
                         Proposer creates candidate
                              │
                              ▼
                    independent Evaluator measures it
                              │
                              ▼
                 result is recorded; Search decides again

    The coordinator owns this loop. This boundary stays the same when the artifact is a prompt, source tree, skill set, dataset recipe, or agent harness.

    No randomness required

    This run and the next search-policy comparison have no random behavior. The proposer always appends the next item in the declared checklist order, so it does not use the supplied proposer context.

    The entire written learning path stays deterministic. A historical number-search benchmark remains under Evidence for readers specifically studying uncertain proposals and recorded random streams. It is not required to understand or use Meta-Evolve's basic loop.

    Check your understanding

    1. Why are there four evaluations but only three trials?
    2. Which component decides that a score of 3 is sufficient?
    3. Can the proposer change the budget?
    4. What does [[], ['outline'], ['outline', 'draft'], ...] describe?
    Answers 1. The seed is evaluated before any successor trial begins. 2. The objective inside `Task` declares `satisfy=3`. 3. No. The coordinator enforces the task and run declarations. 4. The causal lineage of the winning artifact, not merely a list of scores.

    Change and predict

    Append "publish" to ITEMS without changing either budget.

    Predict before running: the path completes outline, draft, and review but cannot append publish, because three trials can create only three successors. The run ends honestly with the best artifact it found; failing to satisfy the objective is not a provider or evaluator failure.

    Restore the file afterward because the committed example is shared evidence.

    Glossary

    Artifact : A versioned value being improved, such as a number, text, source tree, or skill set.

    Candidate : A proposed artifact occurrence with causal parents.

    Evaluation : Independent evidence about one candidate. A typed failure has no score.

    Lineage : The causal path from a result back to its seed.

    Budget : A coordinator-enforced limit on work or resources.

    Experience : Prior recorded observations exposed through bounded push or pull access.

    For the exact API contract, continue to the programming model. For authority and identity invariants, see the architecture.
