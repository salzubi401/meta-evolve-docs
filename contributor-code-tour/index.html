    Trace one run through the kernel

    Run the canonical example once, then keep its two output lines in view:

    uv run python examples/01_number_search/main.py

    12
[0, 1, 6, 11, 12]

    The short script enters one coordinator. The actual order is interleaved:

    declaration
  → encode, evaluate, and atomically commit the seed
  → search decision and commit
  → proposal, candidate encoding, and commit
  → independent evaluation and commit
  → repeat until the committed stop decision
  → reopen the committed stream as a read-only Run

    No stage branches on “number.” The codec handles representation, the proposer handles mutation, the evaluator handles measurement, and search handles the next decision.

    1. Declaration

    examples/01_number_search/main.py declares the task, seed, proposer, search preset, budget, and random seed. The root meta.run export reaches application/runtime.py.

    runtime.run validates the public values, chooses the codec index, computes the effective budget, adapts callables, checks capabilities, prepares search, and derives the run and task identities. Durable-local validation finishes before the coordinator can write an event.

    2. Encoding

    The seed is encoded immediately through CodecIndex.encode. A successor stays a Python value while the proposer works; the one place it becomes a durable payload is proposal_completion.py.

    A codec's TypeError or ValueError means invalid candidate output and becomes a typed failure. Another exception is a codec defect and propagates. Codecs do not choose artifact IDs, parents, scores, or promotion.

    3. Proposal

    execution.py loads only the committed parent artifacts named by the trial. It builds a ProposerContext from recorded randomness, logical step, objectives, bounded context, and audited experience, then calls the replaceable proposer runner.

    proposal_completion.py checks usage and derivation authority before accepting the candidate. Core code creates the proposal, artifact occurrence, stable IDs, parent links, and provenance. The proposer supplies content and evidence; it does not mint durable identity.

    4. Evaluation

    evaluation_execution.py decodes the committed artifact and calls the evaluator. Core code adds one evaluation charge, enforces effective budgets, creates stable evidence and evaluation IDs, and records either metrics or a typed failure.

    The evaluator is outside candidate authority. A candidate can fail a task and receive a real low score. A broken evaluator, exhausted resource, or infrastructure fault carries no metric and cannot be ranked as poor candidate performance.

    5. Search

    run_support.py contains the small drive loop. A prepared policy reads only committed SearchState, returns a trial or stop decision, and the coordinator commits the decision before executing a trial.

    Greedy's parent choice and retention rules live in policies/greedy.py, not in the coordinator. This is why BestOfN, Population, and a conforming custom policy use the same execution path.

    6. Commitment

    coordinator.py funnels every durable fact through commit_batch. It first folds the proposed events on a local projection and checks the same batch grammar recovery uses. Storage.commit then writes events and artifact occurrences together. Only a successful store commit advances the in-memory projection.

    The seed follows the same rule through bootstrap.py: its declaration, occurrence, trial outcome, evidence, and evaluation form one genesis batch. A partial genesis is never a run.

    7. Projection

    projections.py rebuilds RunProjection by folding the ordered event stream. Replay consumes records; it never reruns the proposer, evaluator, context selector, or search policy.

    results.py projects read-only best, trials, lineage, summary, and comparison views. The printed lineage follows committed artifact parent IDs. It omits rejected 16 because that occurrence is not an ancestor of the winning 12.

    Exercises on the invariants

    Authority

    In proposal_completion.py, list the fields copied from proposer output and the fields minted by core. Explain why moving artifact ID creation into the proposer would let a candidate overwrite history.

    Identity

    Change only random_seed in a temporary number-search run. Predict which run identity changes and which task identity stays fixed. Then find both inputs in runtime.py and run_support.py.

    Lineage

    Sketch the parent IDs for attempts 1, 6, 11, 16, and 12. Explain why two artifact occurrences with equal payload bytes still need distinct IDs.

    Budgets

    Account for the example's six evaluations and five successor trials. Identify where the seed is charged, where proposal usage is checked, and where evaluator usage is checked. No component may widen the effective budget.

    Typed failures

    Classify these outcomes: a candidate violates the task, a codec rejects the candidate type, the grader crashes, and a proposer exceeds its resource grant. Only the first can be an ordinary low score.

    Replay

    Read commit_batch beside replay_run_projection. Name the shared fold and grammar checks that keep “committed” equivalent to “recoverable.” Explain why replay must not ask the proposer for the same candidate again.

    Comparison validity

    Use the operations lab to compare Greedy and BestOfN. Then list the declarations that must match before the winner is meaningful. A displayed winner is not evidence when task, evaluator, initial artifact, budget, proposer, or hidden component configuration changed.

    When you can answer all seven exercises from source, continue to the M8 design capstone.
